## 概要

AWS CDK v2.263.0 は、Auto Scaling / DocumentDB / ECS / EKS / Lambda といった主要サービスの L2 API を拡張する新機能を多数含むリリースです。特に EKS では Provisioned Control Plane と Kubernetes 1.36 の両方に対応し、Auto Scaling では新たに追加された CloudFormation の `AutoScalingInstanceRefresh` UpdatePolicy を型付きで扱えるようになりました。Alpha モジュールでは `mediaconnect` の `removalPolicy` プロパティが削除される破壊的変更が含まれる点に注意が必要です。

**リリース:** [v2.263.0](https://github.com/aws/aws-cdk/releases/tag/v2.263.0)

## 新機能

### `autoscaling`: 新しい `AutoScalingInstanceRefresh` UpdatePolicy に対応 ([#38277](https://github.com/aws/aws-cdk/pull/38277))

**この機能でできること:**

- 2026-07-09 に CloudFormation でリリースされた `AutoScalingInstanceRefresh` UpdatePolicy を、`aws-autoscaling` の L2 API から型安全に扱えるようになりました。従来の `rollingUpdate()` / `replacingUpdate()` に加わる 3 つ目の更新戦略で、AMI 変更などの更新をトリガーに `StartInstanceRefresh` API と同じフローで既存インスタンスを段階的に置き換えられます。
- `UpdatePolicy.instanceRefresh(options?)` 静的ファクトリと `InstanceRefreshOptions` インターフェース、および `InstanceRefreshStrategy` / `ScaleInProtectedInstances` / `StandbyInstances` 各 enum が追加され、CloudFormation の生値ではなく enum で戦略を指定できます。
- L1 側にも `CfnUpdatePolicy.autoScalingInstanceRefresh` が追加され、`cloudformation-include` からのラウンドトリップにも対応しています。

**使用例:**

```typescript
import * as cdk from 'aws-cdk-lib';
import * as autoscaling from 'aws-cdk-lib/aws-autoscaling';
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class AsgStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    const vpc = new ec2.Vpc(this, 'Vpc');

    new autoscaling.AutoScalingGroup(this, 'Asg', {
      vpc,
      instanceType: ec2.InstanceType.of(ec2.InstanceClass.T3, ec2.InstanceSize.MICRO),
      machineImage: ec2.MachineImage.latestAmazonLinux2023(),
      // 新しい AutoScalingInstanceRefresh UpdatePolicy を指定
      updatePolicy: autoscaling.UpdatePolicy.instanceRefresh({
        // インスタンス置換方式: ROLLING (デフォルト) または LAUNCH_BEFORE_TERMINATE
        strategy: autoscaling.InstanceRefreshStrategy.ROLLING,
        // 置換中に稼働している必要のあるインスタンス割合の下限 (%) 。デフォルトは 90
        minHealthyPercentage: 90,
        // 置換中に稼働できるインスタンス割合の上限 (%) 。LAUNCH_BEFORE_TERMINATE で有効
        maxHealthyPercentage: 110,
        // 新インスタンス起動後にヘルスチェック合格を待つ時間 (秒)
        instanceWarmup: cdk.Duration.minutes(5),
        // 起動テンプレートに変更がないインスタンスを置換対象から除外するか
        skipMatching: false,
        // 段階的置換のパーセンテージ (checkpointDelay と組み合わせて使用)
        checkpointPercentages: [20, 50, 100],
        // 各チェックポイント間の待機時間
        checkpointDelay: cdk.Duration.minutes(10),
        // 置換完了後、ASG が InstanceRefresh 完了と判定するまでの追加待機時間
        bakeTime: cdk.Duration.minutes(5),
        // 監視する CloudWatch アラーム名 (アラーム発報時にロールバック)
        alarmNames: ['MyAsgUnhealthyAlarm'],
        // スケールイン保護されたインスタンスの扱い: REFRESH / IGNORE / WAIT
        scaleInProtectedInstances: autoscaling.ScaleInProtectedInstances.IGNORE,
        // Standby 状態のインスタンスの扱い: TERMINATE / IGNORE / WAIT
        standbyInstances: autoscaling.StandbyInstances.IGNORE,
      }),
    });
  }
}
```

**ポイント:**

- 引数はすべて任意で、`UpdatePolicy.instanceRefresh()` のように無指定で呼ぶと CloudFormation 側のデフォルト値が適用されます。
- `checkpointPercentages` と `checkpointDelay` はセットで使うことが想定されており、部分的な段階リリース (canary 的なロールアウト) を宣言的に組めます。
- 既存の `rollingUpdate()` / `replacingUpdate()` と併用はできず、`updatePolicy` として 1 つだけを指定します。
- `cloudformation-include` で既存テンプレートを取り込む場合も `AutoScalingInstanceRefresh` セクションが型付きの L1 プロパティとして復元されます。

### `docdb`: `DatabaseCluster` インスタンスごとのメンテナンスウィンドウ設定に対応 ([#38315](https://github.com/aws/aws-cdk/pull/38315))

**この機能でできること:**

- `docdb.DatabaseCluster` に新プロパティ `instanceMaintenanceWindow` が追加され、自動生成される各インスタンスの `PreferredMaintenanceWindow` を明示的に指定できるようになりました。
- 既存の `preferredMaintenanceWindow` はクラスターレベルのみに適用され、インスタンスには渡されていなかったため、これまでは各インスタンスにランダムな 30 分ウィンドウが割り当てられていました。今回の変更でクラスター / インスタンス両方のメンテナンス時間帯を制御できます。
- `preferredMaintenanceWindow` と `instanceMaintenanceWindow` の双方にフォーマット検証が追加され、`ddd:hh24:mi-ddd:hh24:mi` 形式に沿わない値は synth 時に `ValidationError` としてエラーになります。

**使用例:**

```typescript
import * as cdk from 'aws-cdk-lib';
import * as docdb from 'aws-cdk-lib/aws-docdb';
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class DocDbStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    const vpc = new ec2.Vpc(this, 'Vpc');

    new docdb.DatabaseCluster(this, 'Cluster', {
      masterUser: { username: 'admin' },
      instanceType: ec2.InstanceType.of(ec2.InstanceClass.R5, ec2.InstanceSize.LARGE),
      vpc,
      // クラスター全体のメンテナンス時間帯 (従来からあるプロパティ)
      preferredMaintenanceWindow: 'sun:03:00-sun:04:00',
      // v2.263.0 で追加。自動作成される各インスタンスのメンテナンス時間帯
      instanceMaintenanceWindow: 'mon:04:00-mon:05:00',
    });
  }
}
```

**ポイント:**

- インスタンス側のメンテナンスウィンドウが未指定だと DocumentDB 側でランダムに割り当てられ、意図しない時間に自動メンテナンスが走る可能性があるため、明示的に指定することを推奨します。
- クラスターのウィンドウとインスタンスのウィンドウは独立して指定でき、必ずしも同じ時間帯にする必要はありません。フェイルオーバー可用性を確保したい場合は、意図的にずらして設定します。
- 手動で `DatabaseInstance` を追加している場合は、そちらに個別に `preferredMaintenanceWindow` を指定する必要があります。`instanceMaintenanceWindow` は自動生成されるインスタンスにのみ効きます。

### `ecs`: 既存の Cloud Map ネームスペースを ECS クラスターに割り当て可能に ([#36812](https://github.com/aws/aws-cdk/pull/36812))

**この機能でできること:**

- `ecs.Cluster` の `defaultCloudMapNamespace` / `addDefaultCloudMapNamespace()` に、既存の `INamespace` を再利用するための `namespace` プロパティが追加されました。
- 従来は `name` を指定して新規ネームスペースを作成することしかできず、ECS 外で管理している既存の Cloud Map ネームスペースを Service Connect / Service Discovery のデフォルトネームスペースとして指定する手段がありませんでした。
- `namespace` と `name` は排他で、両方指定または両方未指定は synth 時にバリデーションエラーになります。

**使用例:**

```typescript
import * as cdk from 'aws-cdk-lib';
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import * as ecs from 'aws-cdk-lib/aws-ecs';
import * as servicediscovery from 'aws-cdk-lib/aws-servicediscovery';
import { Construct } from 'constructs';

export class EcsStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    const vpc = new ec2.Vpc(this, 'Vpc');

    // ECS の外で先に Cloud Map ネームスペースを作成 (別スタックからのインポートも可)
    const existingNamespace = new servicediscovery.PrivateDnsNamespace(this, 'Namespace', {
      name: 'internal.local',
      vpc,
    });

    const cluster = new ecs.Cluster(this, 'Cluster', {
      vpc,
      defaultCloudMapNamespace: {
        // 新規作成する場合は name を、既存を割り当てる場合は namespace を指定
        namespace: existingNamespace,
        // name と namespace は同時に指定できない (synth 時にエラー)
      },
    });

    // 既存ネームスペースを Service Connect のデフォルトとして使えるようになる
    new ecs.FargateService(this, 'Service', {
      cluster,
      taskDefinition: new ecs.FargateTaskDefinition(this, 'TaskDef'),
      serviceConnectConfiguration: { services: [] },
    });
  }
}
```

**ポイント:**

- 別スタック / 別 AWS アカウントで管理している Cloud Map ネームスペースを ECS クラスターに紐付ける用途に有効です。従来はエスケープハッチや `Cluster` サブクラスでの回避が必要でした。
- `defaultCloudMapNamespace` を後付けで設定する場合は `cluster.addDefaultCloudMapNamespace({ namespace })` を使います。
- クラスター1つに紐づけられるデフォルトネームスペースは 1 つのみで、この動作は変わりません。

### `eks`: Provisioned Control Plane と `controlPlaneScalingTier` プロパティを追加 ([#36651](https://github.com/aws/aws-cdk/pull/36651))

**この機能でできること:**

- EKS の Provisioned Control Plane 機能を L2 コンストラクトから設定できる `controlPlaneScalingTier` プロパティが `ClusterOptions` に追加されました。
- Provisioned Control Plane は、高負荷なワークロードに対して事前にスケール済みのコントロールプレーンを提供する EKS の新機能で、`STANDARD` に加えて `TIER_XL` / `TIER_2XL` / `TIER_4XL` の 4 段階から選択できます。
- 新しい `ControlPlaneScalingTier` enum で型安全に指定でき、未指定時は従来通り CloudFormation 側のデフォルト (オンデマンドスケーリング) が使われます。

**使用例:**

```typescript
import * as cdk from 'aws-cdk-lib';
import * as eks from 'aws-cdk-lib/aws-eks';
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import { KubectlV32Layer } from '@aws-cdk/lambda-layer-kubectl-v32';
import { Construct } from 'constructs';

export class EksStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    const vpc = new ec2.Vpc(this, 'Vpc');

    new eks.Cluster(this, 'Cluster', {
      version: eks.KubernetesVersion.V1_32,
      kubectlLayer: new KubectlV32Layer(this, 'KubectlLayer'),
      vpc,
      // v2.263.0 で追加。Provisioned Control Plane のスケーリング階層を指定
      // STANDARD / TIER_XL / TIER_2XL / TIER_4XL から選択
      controlPlaneScalingTier: eks.ControlPlaneScalingTier.TIER_XL,
    });
  }
}
```

**ポイント:**

- Provisioned Control Plane は追加料金が発生する機能のため、性能要件がある本番ワークロードでのみ利用を検討してください。
- 未指定時は CloudFormation 側でデフォルト動作 (オンデマンドスケーリング) となるため、既存クラスターの動作は変わりません。
- `aws-eks-v2` (実験的な次世代モジュール) 側にも同じ API が追加されています。

### `eks`: Kubernetes 1.36 に対応 ([#38441](https://github.com/aws/aws-cdk/pull/38441))

**この機能でできること:**

- `aws-eks` と `aws-eks-v2` の両モジュールに `KubernetesVersion.V1_36` 定数が追加され、EKS クラスターを Kubernetes 1.36 で作成できるようになりました。
- 対応するツールとして `@aws-cdk/lambda-layer-kubectl-v36` が新たに提供され、kubectl レイヤーとして利用できます。

**使用例:**

```typescript
import * as cdk from 'aws-cdk-lib';
import * as eks from 'aws-cdk-lib/aws-eks';
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import { KubectlV36Layer } from '@aws-cdk/lambda-layer-kubectl-v36';
import { Construct } from 'constructs';

export class EksStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    const vpc = new ec2.Vpc(this, 'Vpc');

    new eks.Cluster(this, 'Cluster', {
      // Kubernetes 1.36 を指定
      version: eks.KubernetesVersion.V1_36,
      // kubectl レイヤーもバージョンを合わせる
      kubectlLayer: new KubectlV36Layer(this, 'KubectlLayer'),
      vpc,
    });
  }
}
```

**ポイント:**

- kubectl レイヤーはクラスターの Kubernetes バージョンに合わせて明示的に指定する必要があります。バージョン不整合があると `kubectl` によるマニフェスト適用が失敗する可能性があります。
- 既存クラスターをアップグレードする場合は EKS の公式ドキュメントに従って段階的に upgrade してください。CDK 上の `version` 変更だけではアプリケーション側の互換性は保証されません。

### `lambda`: Java8AL2023 / Java11AL2023 / Java17AL2023 ランタイムを追加 ([#38419](https://github.com/aws/aws-cdk/pull/38419))

**この機能でできること:**

- Lambda の `Runtime` 定数に、Amazon Linux 2023 ベースの Java 8 / 11 / 17 ランタイム (`JAVA_8_AL2023` / `JAVA_11_AL2023` / `JAVA_17_AL2023`) が追加されました。
- 既存の `JAVA_8` (Amazon Linux 2) / `JAVA_11` / `JAVA_17` からの移行先として、より新しい OS ベースイメージを型安全に指定できます。

**使用例:**

```typescript
import * as cdk from 'aws-cdk-lib';
import * as lambda from 'aws-cdk-lib/aws-lambda';
import { Construct } from 'constructs';

export class LambdaStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    new lambda.Function(this, 'JavaFn', {
      // AL2023 ベースの Java 17 ランタイムを指定
      runtime: lambda.Runtime.JAVA_17_AL2023,
      handler: 'com.example.Handler::handleRequest',
      code: lambda.Code.fromAsset('lambda-jar'),
    });
  }
}
```

**ポイント:**

- Amazon Linux 2 ベースの `JAVA_8` / `JAVA_11` / `JAVA_17` は Lambda 側の廃止スケジュールに沿って順次サポート終了となるため、新規プロジェクトでは AL2023 ベースの新ランタイムを優先することを推奨します。
- ネイティブライブラリを同梱する場合は、AL2 と AL2023 で glibc バージョンなどが異なるため、ビルド環境も AL2023 に合わせておく必要があります。

### `lambda`: `CapacityProvider` に `logGroup` / `systemLogLevel` を追加 ([#38183](https://github.com/aws/aws-cdk/pull/38183))

**この機能でできること:**

- Lambda の Managed EC2 CapacityProvider に、スケーリング活動などのシステムログを CloudWatch Logs に出力するための `logGroup` / `systemLogLevel` プロパティが追加されました。
- L1 (`CfnCapacityProvider`) の `telemetryConfig` を L2 から扱えるようにする変更で、既存の `Function` コンストラクトと同様に、ネストしたインターフェースではなくフラットな props として公開されています。
- 両プロパティが未指定の場合は `TelemetryConfig` 自体が CloudFormation テンプレートに出力されず、サービス側のデフォルト設定が適用されます。

**使用例:**

```typescript
import * as cdk from 'aws-cdk-lib';
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import * as lambda from 'aws-cdk-lib/aws-lambda';
import * as logs from 'aws-cdk-lib/aws-logs';
import { Construct } from 'constructs';

export class CapacityProviderStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    const vpc = new ec2.Vpc(this, 'Vpc');
    const sg = new ec2.SecurityGroup(this, 'Sg', { vpc });
    const logGroup = new logs.LogGroup(this, 'LogGroup');

    new lambda.CapacityProvider(this, 'CP', {
      subnets: vpc.privateSubnets,
      securityGroups: [sg],
      // v2.263.0 で追加。システムログの送信先 CloudWatch Log Group
      logGroup,
      // ログの詳細度。DEBUG / INFO / WARN から選択
      systemLogLevel: lambda.SystemLogLevel.INFO,
    });
  }
}
```

**ポイント:**

- `logGroup` のみ / `systemLogLevel` のみを指定した場合でも `TelemetryConfig` が出力され、残りは Lambda 側のデフォルト値が使われます。
- `SystemLogLevel` は既存の `Function` コンストラクトのものを再利用しており、新しい enum ではありません。
- ログ配信に必要な IAM 権限は Managed EC2 CapacityProvider が使う `AWSLambdaManagedEC2ResourceOperator` マネージドポリシーに含まれているため、追加の権限設定は不要です。

### `lambda`: `CapacityProvider` にタグ伝播 (`PropagateTags`) を追加 ([#38180](https://github.com/aws/aws-cdk/pull/38180))

**この機能でできること:**

- Managed EC2 CapacityProvider が管理する EC2 インスタンス / ENI / EBS ボリュームに対して、指定したタグを伝播させる `propagateTags` プロパティが追加されました。
- タグベースの IAM ポリシーやコスト配分タグを、CapacityProvider が動的に作る下位リソースにも一貫して適用できるようになります。
- `PropagateTags.none()` (明示的に無効化) と `PropagateTags.explicit(tags)` (指定タグのみ伝播) の 2 つのファクトリメソッドが提供されます。省略時は CloudFormation テンプレートに `PropagateTags` が出力されず、API のデフォルト動作が適用されます。

**使用例:**

```typescript
import * as cdk from 'aws-cdk-lib';
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import * as lambda from 'aws-cdk-lib/aws-lambda';
import { Construct } from 'constructs';

export class CapacityProviderTagsStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    const vpc = new ec2.Vpc(this, 'Vpc');
    const sg = new ec2.SecurityGroup(this, 'Sg', { vpc });

    new lambda.CapacityProvider(this, 'CP', {
      subnets: vpc.privateSubnets,
      securityGroups: [sg],
      // 指定したタグを EC2 / ENI / EBS に伝播 (最大 40 個まで)
      propagateTags: lambda.PropagateTags.explicit([
        { key: 'CostCenter', value: 'Engineering' },
        { key: 'Environment', value: 'Production' },
      ]),
      // 明示的にタグ伝播を無効化する場合:
      // propagateTags: lambda.PropagateTags.none(),
    });
  }
}
```

**ポイント:**

- `PropagateTags` はプライベートコンストラクタで、ファクトリメソッド経由でしか生成できないため、無効な組み合わせ (例: `Mode: None` なのに `ExplicitTags` を指定) が構造的に発生しません。
- `explicit()` に渡せるタグ数は最大 40 個までで、synth 時にバリデーションされます。超過するとエラーになります。
- 省略時は CloudFormation に何も出力されず API 側のデフォルト動作となるため、既存構成の挙動には影響しません。

## バグ修正

### `core`: `cloudformation-validate` ライブラリを 1.6.0-beta にアップグレード ([#38444](https://github.com/aws/aws-cdk/pull/38444))

- CDK 内部で CloudFormation テンプレートの静的検証に使っている `cloudformation-validate` を `1.5.1-beta` → `1.6.0-beta` にアップグレードし、これまで CDK 側で `IGNORE_RULES` としてバイパスしていた誤検知の抑制を多数解除しました。
- 主な変更点は次のとおりです。
  - `E3071` (Lambda ZipFile 用の runtime 制限) → `E3677` にリネームされ、`aws-lambda` / `triggers` テストのローカル抑制を削除。グローバル抑制で引き続きカバー。
  - `E3049` (ECS 動的ホストポート) → `W3049` / `I3049` に分割され、無害化。ローカル抑制を削除。
  - `W9009` (deprecated プロパティ) → 上位プロパティに誤って伝播していた警告が修正され、`aws-cloudfront` のバイパスを削除。
  - `E9004` (GetAtt 属性の存在チェック) と `E1152` (AMI ID フォーマット) → 上流で誤検知が修正され、ローカル抑制を削除。

## Alpha モジュール

### `glue-alpha`: 複数のパーティションインデックス作成時の競合状態を修正 ([#38016](https://github.com/aws/aws-cdk/pull/38016))

- Glue テーブルに複数のパーティションインデックスを作成すると、`Index index1 is in CREATING state. Only 1 index can be created or deleted simultaneously per table.` エラーが発生することがあった不具合を修正しました。
- 原因は 2 点あり、(1) パーティションインデックス間のカスタムリソース依存関係が逆向きだったこと、(2) `AwsCustomResource` は `createPartitionIndex` API が HTTP 200 を返した時点で成功とみなすため、実際にはまだ `CREATING` 状態のまま次のインデックス作成が始まってしまうことでした。
- 対処として `isComplete` をポーリングする非同期 Provider ベースのカスタムリソース (`Custom::GluePartitionIndex`) に置き換え、インデックス作成をシリアライズするようになりました。既存名のインデックスは冪等に扱われ、インデックスキーの更新は「delete → 完了確認 → create」の順で行うことでテーブルあたり最大 3 個の上限を超えないようにしています。

**破壊的変更 (Alpha):**

- カスタムリソースの実装が `AwsCustomResource` から Provider ベースに変わり、リソースタイプが `Custom::AWS` → `Custom::GluePartitionIndex` に変更されます。アップグレード後の初回スタック更新でパーティションインデックスのカスタムリソースが置き換えられます。パーティションインデックス自体は状態を持たないためデータ損失はありませんが、リソース置換ログが出力される点に留意してください。
- トークン化 (Ref / Fn::GetAtt など) されたキー名を含むインデックスには、明示的な `indexName` の指定が必須となりました。

**新たに要求される IAM 権限:**

- `glue:CreatePartitionIndex` / `glue:DeletePartitionIndex` / `glue:GetPartitionIndexes` / `glue:GetTable` / `glue:UpdateTable` の 5 権限が、対象のテーブル / データベース / カタログ ARN にスコープされた形でパーティションインデックス用の Lambda ロールに付与されます。

### `mediaconnect`: JSDoc タイポ修正 ([#38434](https://github.com/aws/aws-cdk/pull/38434))

- `aws-mediaconnect-alpha` の JSDoc コメントに残っていた記述ミスの修正です。API の挙動に変更はありません。

## 破壊的変更 (Alpha)

### `mediaconnect`: `FlowProps` / `GatewayProps` / `BridgeProps` から `removalPolicy` を削除 ([#38437](https://github.com/aws/aws-cdk/pull/38437))

`aws-mediaconnect-alpha` の `Flow` / `Gateway` / `Bridge` の各コンストラクトから、意図せず公開されていた `removalPolicy` プロパティが削除されました。これらのリソースは今後 CloudFormation のデフォルトの削除挙動 (`Delete`) に従います。

**変更前:**

```typescript
import * as mediaconnect from '@aws-cdk/aws-mediaconnect-alpha';
import * as cdk from 'aws-cdk-lib';

new mediaconnect.Flow(this, 'Flow', {
  // 以下 (および Gateway / Bridge の同名プロパティ) は v2.263.0 で削除されました
  removalPolicy: cdk.RemovalPolicy.RETAIN,
  // ... その他のプロパティ
});
```

**変更後:**

```typescript
import * as mediaconnect from '@aws-cdk/aws-mediaconnect-alpha';
import * as cdk from 'aws-cdk-lib';

const flow = new mediaconnect.Flow(this, 'Flow', {
  // removalPolicy プロパティは削除。指定しても TypeScript エラーになる
  // ... その他のプロパティ
});

// リソース単位で削除ポリシーを制御したい場合は applyRemovalPolicy() を利用
flow.applyRemovalPolicy(cdk.RemovalPolicy.RETAIN);
```

**移行方法:**

- コンストラクトの props から `removalPolicy` を削除してください。TypeScript は synth 時ではなく型チェックの段階でエラーになるため、ビルド前に検知できます。
- どうしても削除ポリシーを変更したい場合は、生成されたコンストラクトに対して `applyRemovalPolicy()` を呼ぶか、L1 (`CfnFlow` など) を直接触ってエスケープハッチで指定してください。
- Alpha モジュールにおける Break 変更のため、stable モジュールには影響しません。

## まとめ

v2.263.0 は Auto Scaling / DocumentDB / ECS / EKS / Lambda の L2 API 拡充を中心に、実運用で有用な多数の新機能が入ったフィーチャーリリースです。特に Auto Scaling の `AutoScalingInstanceRefresh` UpdatePolicy と EKS の Provisioned Control Plane / Kubernetes 1.36 対応は、大規模ワークロードでの活用余地が大きいアップデートです。一方で `aws-mediaconnect-alpha` からの `removalPolicy` 削除と `aws-glue-alpha` パーティションインデックスの実装差し替えという 2 件の破壊的変更が Alpha モジュールに含まれるため、これらを利用している場合は移行手順を確認したうえでアップグレードしてください。
