## 概要

このリリースでは、CloudFront Origin Access Control に SigV4A + `always-amz-auth` を組み合わせた新しい署名 static (グローバル Lambda Web Function Origin 向け) が追加されました。また、`App` コンストラクトに `confirmValidationPluginsDoNotMutate` プロパティが追加され、synth 速度の改善と検証プラグインのセキュリティ機能のバランスをユーザー側で選択できるようになりました。`NodejsFunction` では esbuild の繰り返し指定可能なオプションをサポートし、`EvaluateExpression` タスクでは state machine ごとに専用の Lambda 関数を生成するフィーチャーフラグが追加されています。あわせて、TypeScript 6 以降での `preCompilation` 失敗など複数のバグ修正が含まれ、CloudFormation L1 リソース定義の更新による破壊的変更にも注意が必要です。

**リリース:** [v2.275.0](https://github.com/aws/aws-cdk/releases/tag/v2.275.0)

## 新機能

### CloudFront: Origin Access Control に SigV4A + always-amz-auth 署名 static を追加 ([#39216](https://github.com/aws/aws-cdk/pull/39216))

**この機能でできること:**
- CloudFront の Origin Access Control (OAC) 用に、`Signing.SIGV4A_ALWAYS_AMZ_AUTH` という新しい static が追加されました。これにより、グローバル (マルチリージョン) の Lambda Web Function Origin が必要とする `sigv4a` プロトコル + `always-amz-auth` 動作を組み合わせた署名設定を 1 行で指定できます。
- v2.274.0 で追加された `SigningProtocol.SIGV4A` ([#38629](https://github.com/aws/aws-cdk/pull/38629)) と `SigningBehavior.ALWAYS_AMZ_AUTH` ([#39196](https://github.com/aws/aws-cdk/pull/39196)) の組み合わせを提供するもので、[#39195](https://github.com/aws/aws-cdk/issues/39195) の最後の残タスクとして実装されました。

**使用例:**

```typescript
import * as cloudfront from 'aws-cdk-lib/aws-cloudfront';
import * as origins from 'aws-cdk-lib/aws-cloudfront-origins';

// グローバル Lambda Web Function Endpoint 向けの OAC
const oac = new cloudfront.FunctionUrlOriginAccessControl(this, 'GlobalLambdaOac', {
  // SigV4A + always-amz-auth の組み合わせ (グローバル Web Function 用)
  signing: cloudfront.Signing.SIGV4A_ALWAYS_AMZ_AUTH,
});

// リージョナル Lambda Web Function Endpoint の場合は従来通り SIGV4_ALWAYS_AMZ_AUTH を使用
const regionalOac = new cloudfront.FunctionUrlOriginAccessControl(this, 'RegionalLambdaOac', {
  signing: cloudfront.Signing.SIGV4_ALWAYS_AMZ_AUTH,
});
```

**ポイント:**
- グローバル Web Function Endpoint は複数リージョンで呼び出されるため、SigV4A による署名が必須です。この static を使うことで、`SigningProtocol` と `SigningBehavior` を個別に指定する必要がなくなります。
- `always-amz-auth` 動作では、オリジンリクエストが常に署名され、ビューワーの `Authorization` ヘッダーが Lambda 関数にそのまま渡されます。
- `aws-cloudfront-origins` の README では、`Authorization` ヘッダーをキャッシュキーに含めるためのカスタムキャッシュポリシー例も追加されています (CloudFront は GET / HEAD リクエストから `Authorization` を既定で除外するため)。

### core: `App` プロパティで CloudFormation Validate プラグインを制御 ([#39452](https://github.com/aws/aws-cdk/pull/39452))

**この機能でできること:**
- これまで組み込みの `CloudFormationValidatePlugin` を無効化するには、`cdk synth --no-validation` または環境変数 `CDK_VALIDATION=false` を使う必要があり、やや分かりにくい構成でした。
- 新しく `App` プロパティ `validationPlugins` (無効化用のフラグ) が追加され、コードから明示的に設定できるようになりました。あわせて関連機能の挙動を制御する `confirmValidationPluginsDoNotMutate` プロパティも追加されています (詳細は後述のバグ修正を参照)。

**使用例:**

```typescript
import * as cdk from 'aws-cdk-lib';

const app = new cdk.App({
  // CloudFormation Validate プラグインを明示的に無効化
  // (従来の cdk synth --no-validation / CDK_VALIDATION=false と同等)
  validationPlugins: false,
});
```

**ポイント:**
- CLI フラグ (`--no-validation`) や環境変数 (`CDK_VALIDATION`) もこれまで通り利用可能で、どちらを使っても最終的な挙動は同じです。
- コード上で宣言的に制御できるようになったことで、IDE での補完やレビュー時の可視性が向上します。

### lambda-nodejs: `esbuildArgs` で引数の繰り返し指定をサポート ([#39344](https://github.com/aws/aws-cdk/pull/39344))

**この機能でできること:**
- `BundlingOptions.esbuildArgs` のプロパティ値として、文字列・真偽値に加えて `string[]` (配列) が指定できるようになりました。
- esbuild が繰り返し指定可能なオプション (`--supported`、`--loader`、`--external` など) について、配列の各要素が `--flag:value` の形で個別の引数として展開されます。これまでは同じフラグを 1 回しか指定できないため、複数の値を渡す必要があるオプションを扱えませんでした。

**使用例:**

```typescript
import * as lambda from 'aws-cdk-lib/aws-lambda';
import * as nodejs from 'aws-cdk-lib/aws-lambda-nodejs';

new nodejs.NodejsFunction(this, 'MyFunction', {
  entry: 'src/handler.ts',
  runtime: lambda.Runtime.NODEJS_22_X,
  bundling: {
    esbuildArgs: {
      // 配列を指定すると、各要素が別々の --supported:... 引数として展開される
      '--supported': [
        'bigint=false',
        'top-level-await=false',
      ],
      // 単一値のオプションはこれまで通り文字列 / 真偽値で指定
      '--log-level': 'warning',
      '--minify': true,
      // コンマ区切りを 1 つの文字列で渡す形式も従来通り動作する
      '--conditions': 'module,import',
    },
  },
});
```

**ポイント:**
- 空配列 (`[]`) を指定した場合は何も展開されません。
- 単一値しか受け付けない esbuild オプションに配列を渡すと esbuild 側で拒否されるため、配列は繰り返し指定が意味を持つフラグに対してだけ使用してください。
- 既存の文字列 / 真偽値 (`'--conditions': 'module,import'` や `'--minify': true` など) の挙動は従来通りです。
- Docker 経由のバンドルとローカル実行の両方で同じ変換ロジックが共有されます。

### L1 CloudFormation リソース定義の更新 ([#39393](https://github.com/aws/aws-cdk/pull/39393))

**この機能でできること:**
- 公開されている CloudFormation Resource Schema に合わせて、L1 リソースの型定義が自動更新されました。各種サービスで新しいプロパティや型が利用可能になります。
- 一部のリソースでは、より正確なスキーマを反映するために型が狭められたり、プロパティが読み取り専用属性に変更されるなどの破壊的変更が含まれています (詳細は後述の「破壊的変更」セクションを参照)。

## バグ修正

### core: 検証プラグイン呼び出しの過剰な防御によるパフォーマンス劣化 ([#39451](https://github.com/aws/aws-cdk/pull/39451))

- これまでコアライブラリは、検証プラグインの実装にバグがある可能性に備えて、プラグイン実行の前後で `cdk.out` ディレクトリ全体のフィンガープリントを計算していました。この処理が synth 全体のパフォーマンス低下を招いていました。
- 修正後は、この挙動はオプトインとなり、必要な場合のみ有効化できます。既定では事前・事後のハッシュ化は行われず、通常ユーザーの synth が高速化します。
- プラグインを自作しており、ファイルを誤って書き換えていないか検証したい場合は、`App` の `confirmValidationPluginsDoNotMutate: true` を指定することで従来の挙動 (ハッシュによる検証) を有効化できます。

```typescript
import * as cdk from 'aws-cdk-lib';

const app = new cdk.App({
  // プラグイン開発中など、cdk.out を書き換えていないか検証したい場合のみ true
  confirmValidationPluginsDoNotMutate: true,
});
```

### stepfunctions-tasks: `EvaluateExpression` タスクごとに専用の Lambda 関数を使用 ([#39436](https://github.com/aws/aws-cdk/pull/39436))

- 従来、同一スタック内で同じランタイム / アーキテクチャを使う `EvaluateExpression` タスクはすべて 1 つの `SingletonFunction` を共有していました。異なる State Machine に属するタスクも同じ関数を参照するため、各 State Machine ロールにはその共有関数に対する `lambda:InvokeFunction` が付与されていました。
- これは、State Machine が自分のタスク以外の関数も呼び出せるという最小権限違反の問題を生んでいました。本修正では、タスクごとに専用の `EvalNodejsFunction` が生成され、State Machine ロールの `lambda:InvokeFunction` もそのタスクの関数のみを対象とするように変更されます。
- フィーチャーフラグ `@aws-cdk/aws-stepfunctions-tasks:evaluateExpressionDedicatedFunction` でこの挙動を制御します。**新規プロジェクトではデフォルトで有効 (true)**、既存プロジェクトはアップグレード時にオプトインでき、`false` を明示すると従来の shared singleton function が維持されます。
- 専用関数は同一スタック内で 1 つの実行ロール (`AWSLambdaBasicExecutionRole` のみを持つ、`immutable: true` な共有ロール) を共有するため、関数の数が増えてもロール数は増えません。

```json
// cdk.json などの context 設定例
{
  "context": {
    "@aws-cdk/aws-stepfunctions-tasks:evaluateExpressionDedicatedFunction": true
  }
}
```

```typescript
import * as sfn from 'aws-cdk-lib/aws-stepfunctions';
import * as tasks from 'aws-cdk-lib/aws-stepfunctions-tasks';

const evaluate = new tasks.EvaluateExpression(this, 'Evaluate', {
  expression: '$.a + $.b',
  resultPath: '$.sum',
});

// フラグが true の場合: この State Machine には evaluate 専用関数の
// lambda:InvokeFunction だけが付与され、他の EvaluateExpression タスクの
// 関数には触れられない
new sfn.StateMachine(this, 'StateMachine', {
  definitionBody: sfn.DefinitionBody.fromChainable(evaluate),
});
```

### lambda-nodejs: TypeScript 6 以降で `preCompilation` が失敗する ([#39401](https://github.com/aws/aws-cdk/pull/39401))

- `NodejsFunction` で `preCompilation: true` を指定した場合、`tsc` を実行して TypeScript コードを事前にコンパイルしますが、TypeScript 6 以降では以下のエラーで失敗していました。

```
error TS5112: tsconfig.json is present but will not be loaded if files are specified on commandline. Use '--ignoreConfig' to skip this error.
```

- これはローカルバンドル (プロジェクトルートから `tsc` を実行) で常に発生し、Docker バンドルでも `workingDirectory` を `tsconfig.json` のあるディレクトリに設定している場合に発生していました。公式バンドルイメージは最新の `typescript` を取得するため、イメージ再ビルドのタイミングで多くのユーザーに影響する可能性がありました。
- 修正では、TypeScript 6 以降の場合のみ `tsc --ignoreConfig` を自動的に付与するようになりました。TypeScript 5 はこのフラグを `TS5023 unknown option` として拒否するため、ローカルでは検出された `tsc` のバージョンに応じて付与を切り替え、Docker ではシェル実行時に `tsc --version` を確認して切り替えます。
- バージョンがパースできない場合はフラグを付与しないため、従来挙動が維持されます。ユーザー側のコード変更は不要です。

## 破壊的変更

L1 リソースは CloudFormation Resource Schema から自動生成されており、CloudFormation の実体を正確に反映するために以下の型変更が行われています ([#39393](https://github.com/aws/aws-cdk/pull/39393))。

### aws-bedrockagentcore: `AWS::BedrockAgentCore::Harness`

- `HarnessAgentCoreMemoryRetrievalConfig.RelevanceScore` の型が `number | string` から `number` に狭まりました。
- `HarnessAgentCoreMemoryRetrievalConfig.TopK` の型が `integer | string` から `integer` に狭まりました。

### aws-codebuild: `AWS::CodeBuild::ReportGroup`

- `Id` 属性が削除されました。

### aws-dax: `AWS::DAX::SubnetGroup`

- `Id` 属性が削除されました。

### aws-dms: `AWS::DMS::MigrationProject`

- `InstanceProfileArn` プロパティが削除され、読み取り専用属性に変更されました。
- `InstanceProfileName` プロパティが削除され、読み取り専用属性に変更されました。
- `MigrationProjectCreationTime` プロパティが削除され、読み取り専用属性に変更されました。

### aws-emr: `AWS::EMR::InstanceFleetConfig`

- `Id` 属性が削除されました。

### aws-fsx: `AWS::FSx::Volume`

- `AggregateConfiguration.Aggregates` プロパティが immutable (作成時のみ指定可) になりました。
- `AggregateConfiguration.ConstituentsPerAggregate` プロパティが immutable になりました。
- `OntapConfiguration.AggregateConfiguration` プロパティが immutable になりました。
- `OntapConfiguration.VolumeStyle` プロパティが immutable になりました。

### aws-medialive: `AWS::MediaLive::Input`

- `InputNetworkLocation` プロパティの型が、`AWS | ON_PREMISES` の string enum に狭まりました。
- `Type` プロパティの型が、16 値の string enum に狭まりました。
- `Tags` プロパティの型が `json` から `Map<string, string>` に狭まりました。
- `RouterDestinationSettings.AvailabilityZoneName` プロパティが必須になりました。
- `RouterSettings.EncryptionType` プロパティの型が、`AUTOMATIC | SECRETS_MANAGER` の string enum に狭まりました。

### aws-medialive: `AWS::MediaLive::InputSecurityGroup`

- `Tags` プロパティの型が `json` から `Map<string, string>` に狭まりました。

### aws-mediapackagev2: `AWS::MediaPackageV2::OriginEndpoint`

- `LowLatencyHlsManifestConfiguration.FilterConfiguration` の型が `LowLatencyHlsFilterConfiguration` に狭まりました。
- `MssManifestConfiguration.FilterConfiguration` の型が `MssFilterConfiguration` に狭まりました。

**移行方法:**

- 削除された `Id` 属性 (`ReportGroup`, `SubnetGroup`, `InstanceFleetConfig`) を参照しているコードは、`Ref` やリソース名ベースの参照に置き換えてください。
- 読み取り専用化された DMS の `InstanceProfileArn` / `InstanceProfileName` / `MigrationProjectCreationTime` は、プロパティとしての指定を削除し、必要であれば `attrInstanceProfileArn` などの属性参照に置き換えてください。
- `FSx::Volume` の immutable 化されたプロパティは、更新時に置き換えが発生するようになります。既存リソースへの変更時はデプロイ計画 (置き換え前提か) を確認してください。
- 型が狭まったプロパティ (`MediaLive`, `MediaPackageV2`, `BedrockAgentCore`) は、`as any` などでキャストしていた場合に明示的な型に修正してください。

## まとめ

v2.275.0 は、CloudFront OAC のグローバル Web Function 対応 (`Signing.SIGV4A_ALWAYS_AMZ_AUTH`)、`App` レベルでの Validate プラグイン制御、`NodejsFunction` の esbuild 繰り返し引数サポートといった実利用に直結する改善と、Step Functions `EvaluateExpression` の IAM 最小権限化や TypeScript 6 対応などのバグ修正が含まれた更新です。CloudFormation L1 定義の破壊的変更が複数のサービスに及んでいるため、該当サービスを利用している場合はアップグレード時の型エラーやデプロイ時の挙動変更を事前に確認することをおすすめします。
