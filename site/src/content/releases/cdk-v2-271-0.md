## 概要

このリリースでは、CodeBuild の Amazon Linux 2023 ホスト選択、Kinesis Analytics での Apache Flink 2.2 サポート、Lambda の S3 Object Storage Mode を利用した自己管理 S3 コード参照、S3 Tables の `tableBucketName` オプション化、`cdk --debug` 時のプロパティトレース表示など複数の新機能が追加されました。加えて、core・ECS・SSM・CloudWatch・EC2 などにおけるバグ修正も含まれています。

**リリース:** [v2.271.0](https://github.com/aws/aws-cdk/releases/tag/v2.271.0)

## 新機能

### CodeBuild の `hostKernel` を `BuildEnvironment` に追加 ([#38513](https://github.com/aws/aws-cdk/pull/38513))

**この機能でできること:**
- CodeBuild がオンデマンドビルドで対応した「ホスト OS カーネルの選択」を L2 で指定できるようになり、Amazon Linux 2023（カーネル 6.x）または Amazon Linux 2（カーネル 4.x）を切り替えられます。
- これまでは L1 のエスケープハッチで `HostKernel` を設定する必要がありました。

**使用例:**

```typescript
import * as codebuild from 'aws-cdk-lib/aws-codebuild';

new codebuild.Project(this, 'MyProject', {
  source: codebuild.Source.gitHub({
    owner: 'my-org',
    repo: 'my-repo',
  }),
  environment: {
    // Linux x86 コンテナ
    buildImage: codebuild.LinuxBuildImage.STANDARD_7_0,
    // 新しく追加された HostKernel enum
    // - LINUX_KERNEL_4  : Amazon Linux 2 (kernel 4.x)
    // - LINUX_KERNEL_6  : Amazon Linux 2023 (kernel 6.x)
    // - LINUX_KERNEL_LATEST : 最新カーネル
    hostKernel: codebuild.HostKernel.LINUX_KERNEL_6,
  },
});
```

**ポイント:**
- `hostKernel` は `LINUX_CONTAINER`、`ARM_CONTAINER`、`LINUX_EC2`、`ARM_EC2` に対して有効です。
- Windows、Mac、Lambda 系のビルドイメージ（`WindowsBuildImage`、`MacBuildImage`、`LinuxLambdaBuildImage`、`LinuxArmLambdaBuildImage`）に指定するとバリデーションエラーになります。
- 未指定の場合は既存の CloudFormation テンプレートに影響がなく（`hostKernel` プロパティは出力されない）、後方互換です。

### Kinesis Analytics Flink に Flink 2.2 サポートを追加 ([#37914](https://github.com/aws/aws-cdk/pull/37914))

**この機能でできること:**
- Amazon Managed Service for Apache Flink が Flink 2.2 に対応したのに合わせて、`@aws-cdk/aws-kinesisanalytics-flink-alpha` の `Runtime` に `FLINK_2_2` が追加されました。

**使用例:**

```typescript
import * as flink from '@aws-cdk/aws-kinesisanalytics-flink-alpha';
import * as s3 from 'aws-cdk-lib/aws-s3';
import { Bucket } from 'aws-cdk-lib/aws-s3';

const bucket = new Bucket(this, 'CodeBucket');

new flink.Application(this, 'MyFlinkApp', {
  code: flink.ApplicationCode.fromBucket(bucket, 'flink-app.jar'),
  // 新たに追加された Flink 2.2 ランタイム
  runtime: flink.Runtime.FLINK_2_2,
});
```

**ポイント:**
- Flink 2.2 は Managed Service for Apache Flink の最新ランタイムです。既存の 1.x 系や 2.0 / 2.1 系のアプリケーションを移行する場合は、[AWS ブログ](https://aws.amazon.com/blogs/big-data/migrate-to-apache-flink-2-2-on-amazon-managed-service-for-apache-flink/)の互換性ガイドを確認してください。

### Lambda の S3 Object Storage Mode サポート ([#38745](https://github.com/aws/aws-cdk/pull/38745))

**この機能でできること:**
- Lambda が対応している「自己管理 S3 コード保存モード（`S3ObjectStorageMode`）」を L2 で直接指定できるようになりました。
- `Code.fromBucketV2()` に `s3ObjectStorageMode` オプションが追加され、Function と LayerVersion の両方で自己バケットからのコード参照を設定できます。

**使用例:**

```typescript
import * as lambda from 'aws-cdk-lib/aws-lambda';
import * as s3 from 'aws-cdk-lib/aws-s3';

const bucket = s3.Bucket.fromBucketName(this, 'CodeBucket', 'my-lambda-code-bucket');

new lambda.Function(this, 'MyFunction', {
  runtime: lambda.Runtime.NODEJS_20_X,
  handler: 'index.handler',
  // fromBucketV2 で s3ObjectStorageMode を指定
  code: lambda.Code.fromBucketV2(bucket, 'functions/my-function.zip', {
    // REFERENCE モードは自バケットからコードを直接参照する
    // S3ObjectStorageMode の値:
    //   - S3ObjectStorageMode.COPY      : Lambda 側にコピー（従来のデフォルト動作）
    //   - S3ObjectStorageMode.REFERENCE : ユーザー管理バケットを直接参照
    s3ObjectStorageMode: lambda.S3ObjectStorageMode.REFERENCE,
    // REFERENCE モードでは objectVersion が必須
    objectVersion: 'exampleVersionId1234567890',
  }),
});
```

**ポイント:**
- `S3ObjectStorageMode.REFERENCE` を利用する場合、`objectVersion` の指定が必須で、未指定時は `S3CodeV2` によるバリデーションエラーとなります。
- `REFERENCE` モードでは、`S3CodeV2` が対象オブジェクトに対して `s3:GetObject` / `s3:GetObjectVersion` を Lambda サービスプリンシパルへ付与するバケットポリシーを自動追加します。KMS カスタマーマネージドキー暗号化バケットの場合、`kms:Decrypt` の鍵ポリシーも追加されます。
- 権限は `aws:SourceAccount` によりアカウント単位に制約され、Function/Layer 名が明示されている場合は `aws:SourceArn` により対象 ARN に絞られます。
- バケットや KMS キーがインポート済みでポリシーが更新できない場合は、既存のリソースポリシー側で必要な権限を用意しておく必要があります。

### S3 Tables の `tableBucketName` をオプション化 ([#37749](https://github.com/aws/aws-cdk/pull/37749))

**この機能でできること:**
- `@aws-cdk/aws-s3tables-alpha` の `TableBucket` で必須だった `tableBucketName` が省略可能になり、他の L2（`aws-s3.Bucket` など）と同じく自動命名できるようになりました。
- 未指定時は `Names.uniqueResourceName` を用いて S3 Tables の命名規則（3-63 文字、英数字とハイフン、先頭・末尾が英数字）に準拠した名前が自動生成されます。

**使用例:**

```typescript
import * as s3tables from '@aws-cdk/aws-s3tables-alpha';

// tableBucketName を指定しない場合、自動でユニーク名が生成される
// 生成例: autonamedteststack-autonamedbucket-ab3a2b45
new s3tables.TableBucket(this, 'AutoNamedBucket');

// もちろん従来通り明示指定も可能
new s3tables.TableBucket(this, 'NamedBucket', {
  tableBucketName: 'my-explicit-table-bucket-name',
});
```

**ポイント:**
- 既存コードで `tableBucketName` を指定している箇所には影響しません。
- 内部的には `Lazy.string + Names.uniqueResourceName` パターンを利用しており、これは `TrustStore` や `KeyValueStore` などの L2 と同じ実装パターンです。

### `cdk --debug` でプロパティのスタックトレースを表示 ([#38844](https://github.com/aws/aws-cdk/pull/38844))

**この機能でできること:**
- `CDK_DEBUG=true`（`cdk --debug` / `--debug-app` で有効化）で synth した場合、コンストラクト生成時のスタックトレースに加え、CloudFormation リソースのプロパティが変更される箇所のスタックトレースも記録されるようになりました。
- これらのトレースは `CloudFormationValidatePlugin` の検出結果とリンクされ、テンプレートのバリデーションで検出された問題について「そのプロパティが設定されている全ての位置」がレポートに表示されます。

**使用例:**

```bash
# 通常の synth ではプロパティのトレースは取得されない
cdk synth

# --debug を付けて実行すると、CloudFormationValidatePlugin の検出結果に
# プロパティを設定したコード位置がまとめてレポートされる
cdk synth --debug
```

**ポイント:**
- 大規模なアプリでは常時トレース取得はコストが高いため、`--debug` フラグを付けたときのみ有効になります。
- CloudFormation テンプレートに問題があった際、原因となったプロパティ設定箇所の特定が容易になります。

## バグ修正

### CloudFormation バリデーションエンジンを最新版へアップグレード ([#38884](https://github.com/aws/aws-cdk/pull/38884))
- `@aws/cloudformation-validate` を 1.12.1 にアップグレード。
- Rego ではなく純粋な Rust で評価する `CompositeEngine` に切り替わり（カスタム Rego ルールは引き続きサポート）、パフォーマンスとメモリ使用量が大幅に改善されました。
- スキーマの問題（[#38531](https://github.com/aws/aws-cdk/issues/38531) など）が修正され、最新リソーススキーマが取り込まれています。
- 詳細レベルは `STANDARD` に切り替えられました。

### ECS `TagParameterContainerImage` でダイジェスト参照をサポート ([#37868](https://github.com/aws/aws-cdk/pull/37868))
- これまで `TagParameterContainerImage` の `bind()` は常に `repositoryUriForTag()` を呼び、リポジトリ URI とパラメータ値の区切りに `:` が使われていました。CloudFormation Parameter に `sha256:...` のダイジェストを渡した場合、正しい区切り文字である `@` が使えず ECS が正しく参照できませんでした。
- `imageDigest?: boolean` オプション（デフォルト `false`、既存挙動と互換）を追加し、`true` を指定すると内部で `repositoryUriForDigest()` を利用して `@` 区切りの URI を出力するようになりました。

**修正後の使用例:**

```typescript
import * as ecs from 'aws-cdk-lib/aws-ecs';
import * as ecr from 'aws-cdk-lib/aws-ecr';

const repository = ecr.Repository.fromRepositoryName(this, 'Repo', 'my-repo');

const image = new ecs.TagParameterContainerImage(repository, {
  // パラメータでダイジェスト（sha256:...）を渡す場合に true を指定
  imageDigest: true,
});

const taskDefinition = new ecs.FargateTaskDefinition(this, 'TaskDef');
taskDefinition.addContainer('web', {
  image: ecs.ContainerImage.fromEcrRepository(repository),
});
```

### `secret.fromSsmParameter` の W2001 警告を修正 ([#38833](https://github.com/aws/aws-cdk/pull/38833))
- `secret.fromSsmParameter` を使用すると、参照されない場合でも `CfnParameter` が常に生成され、CloudFormation の W2001（未使用パラメータ）警告が発生していました。
- 修正により、実際に値が参照されるときにのみパラメータを生成するようになり、W2001 の誤警告が出なくなりました。

### CloudWatch の IQM アラームが正しくレンダリングされない問題を修正 ([#38834](https://github.com/aws/aws-cdk/pull/38834))
- IQM（Interquartile Mean）が単純な `Statistic` として扱われていましたが、実際は `ExtendedStatistic` として扱う必要がありました。
- 併せて内部のメトリクスパース処理が整理され、未使用機能（"can be rendered as single param statistic"）が取り除かれています。

### ネストスタックにおける `resolveReferences` のパフォーマンス改善 ([#38813](https://github.com/aws/aws-cdk/pull/38813))
- ネストスタックを持つアプリの synth 時に行う `resolveReferences` の 2 回目のパスが、コンストラクトツリー全体を再走査していました。
- 新関数 `resolveReferencesInElements` を導入し、2 回目のパスではネストスタックアセットを受け取ったコンストラクトのみを再解決するように修正。
- 多数のネストスタックを持つ実測ケースで、2 回目のパスにかかる時間が **3,404ms → 35ms** に短縮されています。

### 同一コンストラクトでの `acknowledgeWarning` が無視される問題を修正 ([#38821](https://github.com/aws/aws-cdk/pull/38821))
- `Annotations.of(scope).acknowledgeWarning(id)` は「サブツリー全体で有効」と文書化されていますが、**同じ**コンストラクトで警告発火より先に acknowledge を呼び出しても警告が抑制されていませんでした（発火→ ack や、祖先→子孫の順は動作）。
- 内部の `Acknowledgements.searchPaths()` がノード自身のフルパスを返却リストに含めていなかった不具合を修正。同じ問題を抱えていた `acknowledgeInfo()` / `addInfoV2()` も同時に修正されています。

**修正後の使用例:**

```typescript
import { Annotations } from 'aws-cdk-lib';

// 同じコンストラクトで先に acknowledge しても、警告が正しく抑制されるようになった
Annotations.of(construct).acknowledgeWarning('some-warning-id');
Annotations.of(construct).addWarningV2('some-warning-id', 'This warning is acknowledged');
```

### `validations.acknowledge()` がスコープを尊重しない問題を修正 ([#38789](https://github.com/aws/aws-cdk/pull/38789))
- バリデーション抑制の適用スコープを考慮せずに「どのルールが抑制されているか」が決まっていました。
- 各リソースに最も近い suppression を適用するように変更され、違反レポートの `{ rule, resources }` 構造の中でリソースごとに異なる suppression 理由を正しく報告できるようになりました。
- 併せて JSON フォーマット時に `logicalId` から `constructPath` を推論していた処理を、違反処理の段階の独立ステップに切り出しています。

### EC2 の synth-time AMI ルックアップで W9010 が出る問題を修正 ([#38840](https://github.com/aws/aws-cdk/pull/38840))
- W9010 は「テンプレートに AMI ID がハードコードされている」を検出するチェックですが、synth 時 AMI ルックアップの結果もテンプレートに AMI ID として現れるため誤検出されていました。
- synth 時ルックアップの場合は自動的に警告が acknowledge されるようになり、W9010 の誤警告が出なくなりました。

### CloudAssembly のバリデーションで `Invalid URL` エラーが発生する問題を修正 ([#38867](https://github.com/aws/aws-cdk/pull/38867))
- Node.js 24.20.0 以降で導入された WHATWG URL 準拠の新パーサーにより、`aws-cdk-lib/cloud-assembly-schema` の CloudAssembly バリデータでエラーが発生していました。
- `@aws-cdk/cloud-assembly-schema` の依存を更新して問題を解消。存在しないヘルパースクリプトへの参照も削除されました。

### テレメトリの synth 時間モデル関連の修正 ([#38889](https://github.com/aws/aws-cdk/pull/38889))
- テレメトリの数値が synth 時間モデル化に十分な形になっていない問題への対応です。

## まとめ

CodeBuild の Amazon Linux 2023 対応、Flink 2.2、Lambda の S3 Object Storage Mode、S3 Tables の自動命名など、複数の実用的な L2 拡張が入ったリリースです。加えて、ネストスタックの synth 高速化や Annotations の acknowledge 修正など、大規模アプリの synth 挙動改善につながる修正も含まれています。
