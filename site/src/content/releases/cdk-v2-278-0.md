## 概要

このリリースでは Lambda 関連で、Lambda Managed Instances 上の関数で GPU アクセラレータを設定できる `AcceleratorConfig` のサポートと、Customer-Managed Runtimes (CMR) 向けに `RuntimeConfig` を設定する `FunctionRuntimeConfig` mixin が追加されました。あわせて API Gateway のプロキシリソース向け path parameter 自動設定、EC2 サブネットでの IPAM CIDR 割り当て、RDS `DatabaseInstance` の CloudWatch メトリクスヘルパー、ELBv2 の RFC 9151 (CNSA 1.0) SSL ポリシーと正規表現マッチングのリスナー条件、self-managed Kafka の queue 消費モードなど、幅広い L2 の機能強化が行われています。また `core` では、アセットが実際に bundling される時のみ Docker イメージをビルドする最適化と、CloudFormation テンプレートに構造化された設計コンテキスト (MetadataContext) を埋め込む API が追加されました。

**リリース:** [v2.278.0](https://github.com/aws/aws-cdk/releases/tag/v2.278.0)

## 新機能

### lambda: Lambda Managed Instances 向け AcceleratorConfig サポート ([#39806](https://github.com/aws/aws-cdk/pull/39806))

**この機能でできること:**
- Lambda Managed Instances 上で動作する Lambda 関数に GPU アクセラレータを設定できるようになりました。新しい `acceleratorConfig` プロパティと `AcceleratorMemorySize` enum-like クラスが追加されています。
- 関連する `TargetTrackingScalingPolicy.gpuUtilization()` メソッドも追加され、`LambdaCapacityProviderAverageGPUUtilization` メトリクスでスケーリングできます。

**使用例:**

```typescript
import * as lambda from 'aws-cdk-lib/aws-lambda';
import * as ecr from 'aws-cdk-lib/aws-ecr';

// GPU 用のキャパシティプロバイダー
const capacityProvider = new lambda.CapacityProvider(this, 'Gpu', {
  // g6.xlarge などの GPU 付き x86_64 インスタンスを指定
  instanceTypes: [new ec2.InstanceType('g6.xlarge')],
  architecture: lambda.Architecture.X86_64,
});

// gpuUtilization でターゲット追跡スケーリング (0-100 で指定、範囲外は synth で失敗)
capacityProvider.scaleOnTargetTrackingMetric('Gpu', {
  policy: lambda.TargetTrackingScalingPolicy.gpuUtilization({ targetValue: 70 }),
});

const fn = new lambda.Function(this, 'Fn', {
  // コンテナイメージ必須 (Runtime.FROM_IMAGE 以外は synth で失敗)
  runtime: lambda.Runtime.FROM_IMAGE,
  handler: lambda.Handler.FROM_IMAGE,
  code: lambda.Code.fromEcrImage(ecr.Repository.fromRepositoryName(this, 'Repo', 'my-repo')),
  // x86_64 必須
  architecture: lambda.Architecture.X86_64,
  // 明示的な memorySize >= 2048 MiB 必須
  memorySize: 4096,
  // アクセラレータメモリサイズ: 定義済み値のほか AcceleratorMemorySize.of() も利用可能
  acceleratorConfig: {
    acceleratorMemorySize: lambda.AcceleratorMemorySize.GIB_24,
    // 他のサイズ: GIB_3 / GIB_6 / GIB_12 / GIB_16 / GIB_24 / GIB_48
  },
  // acceleratorConfig を使う場合 ephemeralStorageSize は最大 32 GiB まで指定可能 (通常は 10 GiB)
  ephemeralStorageSize: cdk.Size.gibibytes(20),
});

// キャパシティプロバイダーへの関数のアタッチが必須 (ない場合は synth 時に失敗)
capacityProvider.addFunction(fn);
```

**ポイント:**
- `acceleratorConfig` を設定する関数には以下の制約があり、違反すると synth 時に失敗します: (1) コンテナイメージ関数であること (`Runtime.FROM_IMAGE`)、(2) `x86_64` アーキテクチャであること、(3) `memorySize` を明示指定し 2048 MiB 以上であること。
- `AcceleratorMemorySize.of()` は未モデル化の新しい値を渡すための escape hatch です。負数や非整数は拒否され、トークンはスキップされます。実際の有効値はサービスがデプロイ時に検証します。
- `acceleratorConfig` を既存関数で変更すると関数は置き換えられる (replace) ことが `addInfoV2` 経由の annotation で通知されます。
- `cpuUtilization()` と `gpuUtilization()` のターゲット値は 0〜100 の範囲外だと synth で拒否されます (サービス側のデプロイ時バリデーションと同じ)。

### lambda: Customer-Managed Runtimes 向け FunctionRuntimeConfig mixin ([#39834](https://github.com/aws/aws-cdk/pull/39834))

**この機能でできること:**
- Customer-Managed Runtimes (CMR) により、独自の ECR イメージベースの Lambda ランタイムを公開・管理して関数に紐付けられるようになりました。新しい `lambda.mixins.FunctionRuntimeConfig` mixin で、既存の `Function` に `RuntimeConfig` (ランタイム ARN とエイリアス) を適用できます。
- このリリースは**コンシューマ側のみ** (ランタイムを利用する側) の GA スコープです。ランタイム公開側の L2 (`Runtime` / `RuntimeVersion` / `RuntimeAlias`) は post-GA で追加される予定です。

**使用例:**

```typescript
import * as lambda from 'aws-cdk-lib/aws-lambda';
import * as path from 'path';

// 'custom' ランタイムで Function を定義し、mixin で RuntimeConfig を適用
new lambda.Function(this, 'MyFunction', {
  // Customer-Managed Runtime は 'custom' ランタイム名で指定
  runtime: new lambda.Runtime('custom', lambda.RuntimeFamily.OTHER),
  handler: 'index.handler',
  code: lambda.Code.fromAsset(path.join(__dirname, 'lambda-handler')),
}).with(new lambda.mixins.FunctionRuntimeConfig({
  // ランタイムの ARN (別アカウントから共有されたものも string で指定可能)
  runtimeArn: 'arn:aws:lambda:us-east-1:123456789012:runtime/my-python-runtime',
  // 使用するランタイムエイリアス
  runtimeAlias: 'stable',
}));
```

**ポイント:**
- Mixin を適用した関数以外は影響を受けません。関数のランタイムが `custom` でない、またはコンテナイメージ関数の場合は synth 時に失敗します。
- `custom` ランタイムで `RuntimeConfig` を設定していない関数は、`@aws-cdk/aws-lambda:customRuntimeRequiresRuntimeConfig` という info annotation が出ます (サービスがデプロイ時に拒否するため)。この ID は公開契約として固定化されており、`node.addMetadata` で acknowledge 可能です。
- `runtimeArn` / `runtimeAlias` は正規表現検証や API 呼び出しを行わず、トークンもそのまま通過します。
- `runtimeAlias` を変更すると関数の新しいバージョンが発行されます。
- 将来的に `Function` 本体に `runtimeConfig` プロパティを追加する際にも、この mixin が利用される設計です。CMR が各リージョン / パーティションで un-gate されるまでは mixin 経由で利用します。

### apigateway: プロキシリソースの path parameter 自動設定 ([#37124](https://github.com/aws/aws-cdk/pull/37124))

**この機能でできること:**
- `ProxyResourceOptions` に `autoConfigurePathParameter: boolean` が追加され、`addProxy()` でプロキシリソースを作る際に、メソッド側 (`method.request.path.proxy: true`) と統合側 (`integration.request.path.proxy: 'method.request.path.proxy'`) の path parameter 設定を自動で行えるようになりました。
- これまでは `/api/foo/bar` へのリクエストが `/api/` として転送されるなど、手動設定が必要でした。AWS マネジメントコンソールと同じ挙動を CDK でも実現できます。

**使用例:**

```typescript
import * as apigateway from 'aws-cdk-lib/aws-apigateway';

const api = new apigateway.RestApi(this, 'Api');
const resource = api.root.addResource('api');

// autoConfigurePathParameter: true で path parameter が自動設定される
resource.addProxy({
  defaultIntegration: new apigateway.HttpIntegration('https://backend.example.com/{proxy}', {
    httpMethod: 'ANY',
    options: {
      requestParameters: {
        // ユーザー定義のパラメータは自動設定より優先される
        'integration.request.header.X-Forwarded-Host': 'method.request.header.Host',
      },
    },
  }),
  // 新プロパティ: デフォルトは false (既存挙動を維持)
  autoConfigurePathParameter: true,
});
```

**ポイント:**
- デフォルトは `false` のため、既存ユーザーの CloudFormation テンプレートは変化しません (opt-in 方式)。
- ユーザーが明示的に設定した `requestParameters` は自動設定より優先されます。
- CORS プリフライト用の mock integration (`OPTIONS`) は変更されません。
- プロキシをルート直下 (`/{proxy+}`) にマウントした場合、ルートリソース自体のメソッドには自動設定されません (ルートには `{proxy}` path parameter が存在しないため)。

### core: アセット bundling 時のみ Docker イメージをビルド ([#39778](https://github.com/aws/aws-cdk/pull/39778))

**この機能でできること:**
- 新しい `DockerImage.fromBuildOnDemand()` ファクトリが追加され、イメージを即座にビルドせず、実際に `run()` / `cp()` / アセット staging から参照された際にのみビルドするようになりました。
- 既存の `fromBuild()` と同じタグ・ハッシュを生成するため、切り替えてもアセットハッシュは変わりません。`PythonFunction` と `PythonLayerVersion` は内部で `fromBuildOnDemand()` を使うように変更されました。

**使用例:**

```typescript
import * as cdk from 'aws-cdk-lib';

// 必要になるまでビルドを遅延する
const image = cdk.DockerImage.fromBuildOnDemand('./docker-build-context', {
  buildArgs: { SOME_ARG: 'value' },
});

// アセット staging でこのイメージを bundling に使うときに初めてビルドされる
new cdk.aws_lambda.Function(this, 'Fn', {
  runtime: cdk.aws_lambda.Runtime.PYTHON_3_12,
  handler: 'index.handler',
  code: cdk.aws_lambda.Code.fromAsset('./lambda-src', {
    bundling: {
      image,
      command: ['bash', '-c', 'pip install -r requirements.txt -t /asset-output && cp -au . /asset-output'],
    },
  }),
});
```

**ポイント:**
- ビルド済みイメージは次の `App` が作成されるまで記憶されるため、同じタグのイメージを使う他のインスタンスは再ビルドおよび `docker image inspect` をスキップします。キーはタグ + Docker プログラム + `DOCKER_HOST` + `DOCKER_CONTEXT`。
- `buildContexts` を使うイメージはタグがコンテキストをカバーしないため、キャッシュされません。
- イメージが削除された後にコンテナ作成が失敗 (exit code 125) した場合、再実行で再ビルドされることを示す改善されたエラーメッセージが出力されます。
- CI での PythonFunction を含む synth 時間の中央値で、繰り返し synth の場合 `3.71s → 1.37s`、イメージが削除された状態では `14.93s → 1.52s` と大幅な短縮が報告されています。
- `fromBuild()` は従来通り即時ビルドする挙動を維持します。アセット bundling のみに使うイメージは `fromBuildOnDemand()` が推奨されます。

### core: 合成テンプレートへの構造化設計コンテキスト埋め込み (MetadataContext) ([#38381](https://github.com/aws/aws-cdk/pull/38381))

**この機能でできること:**
- CloudFormation が定義する `com.aws.cloudformation.Context` メタデータスキーマに沿って、合成されたテンプレートへ設計コンテキスト (理由、不変条件、変更安全性ガイダンス、provenance 等) を型付き API で埋め込めるようになりました。
- 新 API: リソース単位の `CfnResourceMetadataContext` と、テンプレート単位の `CfnTemplateMetadataContext` の 2 つの Aspect が追加されています。

**使用例:**

```typescript
import * as cdk from 'aws-cdk-lib';

// 特定のリソースに Context メタデータを付与
cdk.CfnResourceMetadataContext.set(scope, {
  resource: {
    purpose: 'Primary database for the order service',
    mutable: 'immutable',
  },
  mutability: {
    // sparse マップ: resource.mutable のデフォルトと異なるプロパティのみ記述
    'StorageEncrypted': 'immutable',
  },
  trust: {
    // trust データは検証される (不正な構造は synth で拒否)
    owner: 'team-orders',
  },
});

// テンプレート全体に Context を付与
cdk.CfnTemplateMetadataContext.set(stack, {
  template: {
    purpose: 'Order processing service',
    businessOwner: 'team-orders',
  },
});
```

**ポイント:**
- 既存アプリは、この新 API を呼び出さない限り合成結果が変わりません。
- `IConstructSelector` でリソースのターゲティングを行い、デフォルトでは `CfnResource` スコープまたはその直下の `CfnResource` デフォルト子が対象になります。
- 上書きは暗黙的なマージではなく、完全値の置換で行われます。Aspect の priority とスコープで、どの操作が最後に適用されるかが決まります。
- `NestedStack` の境界は保持され、`Stage` アセンブリ境界を越えることはありません。
- `CfnResource` にマッチしないセレクタ、不正な trust データ、`mutable` デフォルトと重複する `mutability` エントリ、トップレベル template Context の未解決値は拒否されます。

### ec2: Subnet での IPAM CIDR 割り当てサポート ([#38810](https://github.com/aws/aws-cdk/pull/38810))

**この機能でできること:**
- `Subnet` (および `PublicSubnet` / `PrivateSubnet`) に、Amazon VPC IP Address Manager (IPAM) プールから IPv4 CIDR を割り当てるための `ipv4IpamAllocation` プロパティが追加されました。`cidrBlock` はオプショナルになり、IPAM 経由で動的に割り当てる場合は省略します。

**使用例:**

```typescript
import * as ec2 from 'aws-cdk-lib/aws-ec2';

const vpc = new ec2.Vpc(this, 'Vpc', {
  ipAddresses: ec2.IpAddresses.cidr('10.0.0.0/16'),
});

// 既存の IPAM プールを参照する場合
const ipamPool = ec2.CfnIPAMPool.fromIpamPoolId(this, 'Pool', 'ipam-pool-0abc1234');

new ec2.Subnet(this, 'IpamSubnet', {
  vpcId: vpc.vpcId,
  availabilityZone: 'us-east-1a',
  // cidrBlock を省略し、代わりに ipv4IpamAllocation を指定 (両方指定は synth で失敗)
  ipv4IpamAllocation: {
    ipamPool,
    // /16 から /28 までの範囲 (ec2 パッケージの NetworkBuilder と同じ制約; トークンはスキップ)
    netmaskLength: 24,
  },
});
```

**ポイント:**
- `cidrBlock` と `ipv4IpamAllocation` のどちらか一方を指定する必要があります。両方指定または両方未指定は synth 時に失敗します。
- IPAM 経由で割り当てた場合、`subnet.ipv4CidrBlock` は `CfnSubnet.attrCidrBlock` (デプロイ時トークン) になります。`SubnetFilter.byCidrMask()` / `byCidrRanges()` / `containsIpAddresses()` などの CIDR を parse する処理は使えません。
- `ipamPool` は `IIPAMPoolRef` 型で、`CfnIPAMPool.fromIpamPoolId()` で既存プールもインポートできます。
- IPv6 IPAM 割り当てや、プールのデフォルトネットマスクを使う機能は今後のフォローアップ対応です。

### elbv2: RFC 9151 (CNSA 1.0) SSL セキュリティポリシー追加 ([#38700](https://github.com/aws/aws-cdk/pull/38700))

**この機能でできること:**
- ALB の HTTPS リスナーと NLB の TLS リスナーで利用可能な、RFC 9151 (CNSA 1.0) 準拠の 7 つの SSL セキュリティポリシーが `SslPolicy` enum に追加されました。

**使用例:**

```typescript
import * as elbv2 from 'aws-cdk-lib/aws-elasticloadbalancingv2';

const alb = new elbv2.ApplicationLoadBalancer(this, 'Alb', { vpc, internetFacing: true });

alb.addListener('Https', {
  port: 443,
  protocol: elbv2.ApplicationProtocol.HTTPS,
  certificates: [elbv2.ListenerCertificate.fromArn('arn:aws:acm:...')],
  // RFC 9151 準拠の厳格ポリシー (TLS 1.3 / TLS 1.2)
  sslPolicy: elbv2.SslPolicy.RFC9151_TLS13_13,
  // ほかに利用可能な値:
  // Strict: RFC9151_TLS13_12, RFC9151_TLS13_12_EXT0
  // Interop (段階的移行向け): RFC9151_TLS13_12_INTEROP1 / INTEROP2 / INTEROP3 / INTEROP4
  defaultAction: elbv2.ListenerAction.fixedResponse(200),
});
```

**ポイント:**
- Strict ポリシーは RFC 9151 の要件をフルに強制し、Interop ポリシーは RFC 9151 と非 RFC 9151 の暗号方式を混在させ段階的に移行可能にします。
- 既存の CloudFormation デフォルト (`ELBSecurityPolicy-2016-08`) や挙動は変わりません。feature flag もありません。
- 各ポリシーのドキュメントコメントに、サポートする TLS バージョンと暗号方式、AWS ドキュメントへのリンクが含まれます。

### elbv2: リスナー条件の正規表現サポート ([#36384](https://github.com/aws/aws-cdk/pull/36384))

**この機能でできること:**
- ALB のリスナールールで正規表現マッチングが使えるようになり、`ListenerCondition` に 3 つの新メソッドが追加されました: `hostHeadersRegex()` / `httpHeaderRegex()` / `pathPatternsRegex()`。
- これらは CloudFormation の `RegexValues` プロパティにレンダリングされます。

**使用例:**

```typescript
import * as elbv2 from 'aws-cdk-lib/aws-elasticloadbalancingv2';

listener.addAction('Regex', {
  priority: 10,
  conditions: [
    // ホストヘッダの正規表現マッチ
    elbv2.ListenerCondition.hostHeadersRegex(['^api-(dev|stg)\\.example\\.com$']),
    // HTTP ヘッダの正規表現マッチ
    elbv2.ListenerCondition.httpHeaderRegex('X-Custom-Header', ['^v[0-9]+$']),
    // パスパターンの正規表現マッチ
    elbv2.ListenerCondition.pathPatternsRegex(['^/api/v[0-9]+/.*']),
  ],
  action: elbv2.ListenerAction.forward([targetGroup]),
});
```

**ポイント:**
- 既存のリスナー条件 (非 regex を含む) にも入力長・文字種チェックが追加されました: ホストヘッダ値・HTTP ヘッダ値・パスパターン値は 128 文字以内、HTTP ヘッダ名は 40 文字以内、HTTP リクエストメソッドは `[A-Z-_]+` のパターンに合致する必要があります。
- これらの検証は、既に Elastic Load Balancing がデプロイ時に拒否していた入力を synth 時に前倒ししたもので、合法な使い方は影響を受けません。
- 未解決トークン (SSM parameter lookup、CloudFormation parameter、他リソースの属性) は synth 時に長さ・文字種がわからないため、検証をスキップしサービス側のデプロイ時検証に委ねます。
- パスパターンの最大数 5 は従来通りで、エラーメッセージとコードも維持されています。

### rds: DatabaseInstance の CloudWatch メトリクスヘルパー ([#37931](https://github.com/aws/aws-cdk/pull/37931))

**この機能でできること:**
- 新しい `DatabaseInstanceMetrics` Facade が追加され、`DatabaseInstance` / インポートされたインスタンス / `CfnDBInstance` のいずれに対しても、`AWS/RDS` 名前空間の主要メトリクスに対する型付きヘルパーが提供されます。
- IDE 補完・コンパイル時型チェックで、文字列指定による typo を防げます。

**使用例:**

```typescript
import * as rds from 'aws-cdk-lib/aws-rds';
import * as cloudwatch from 'aws-cdk-lib/aws-cloudwatch';

const instance = new rds.DatabaseInstance(this, 'Db', { /* ... */ });

// L2 / インポート / CfnDBInstance いずれでも同じ使い方
const metrics = rds.DatabaseInstanceMetrics.fromDatabaseInstance(instance);

// 利用可能なヘルパー (全てデフォルトで Average 統計):
// CPU & メモリ: cpuUtilization, freeableMemory, swapUsage
// 接続 & レイテンシ: databaseConnections, readLatency, writeLatency
// ストレージ: freeStorageSpace, burstBalance
// I/O: readIOPS, writeIOPS, readThroughput, writeThroughput, diskQueueDepth
// ネットワーク: networkReceiveThroughput, networkTransmitThroughput
// レプリケーション: replicaLag
new cloudwatch.Alarm(this, 'ReplicaLag', {
  metric: metrics.replicaLag(),
  threshold: 60,
  evaluationPeriods: 3,
});

// 公開された metric() 経由でエンジン固有のメトリクスも参照可能
const binLog = metrics.metric('BinLogDiskUsage');
```

**ポイント:**
- `DatabaseInstanceBase` / `IDatabaseInstance` 自体には変更がなく、既存の `metricXxx()` メソッドはそのまま残ります。Facade は `IDBInstanceRef` のみに依存するため `CfnDBInstance` でも使えます。
- メトリクスは内部で `.attachTo(instance)` を呼ぶため、別環境から利用する場合でもアカウントとリージョンが正しく保持されます。

### lambda-event-sources: self-managed Kafka の queue 消費モードサポート ([#39712](https://github.com/aws/aws-cdk/pull/39712))

**この機能でできること:**
- Lambda が self-managed Kafka トピックを consumer group ではなく share group (queue セマンティクス、KIP-932) として消費できるようになり、CDK でも `consumptionMode` で指定できるようになりました。
- 新しい `KafkaConsumptionMode` enum-like クラス (`STREAM` / `QUEUE` / `of()`) が追加されています。

**使用例:**

```typescript
import * as lambda from 'aws-cdk-lib/aws-lambda';
import * as sources from 'aws-cdk-lib/aws-lambda-event-sources';
import * as secretsmanager from 'aws-cdk-lib/aws-secretsmanager';

fn.addEventSource(new sources.SelfManagedKafkaEventSource({
  bootstrapServers: ['kafka.example.com:9092'],
  topic: 'my-topic',
  secret: secretsmanager.Secret.fromSecretNameV2(this, 'Secret', 'my-kafka-secret'),
  authenticationMethod: sources.AuthenticationMethod.SASL_SCRAM_512_AUTH,
  // queue モード: startingPosition / startingPositionTimestamp / retryAttempts: -1 は指定不可
  consumptionMode: lambda.KafkaConsumptionMode.QUEUE,
  // stream モードの場合は startingPosition が必須 (synth で検証)
  // consumptionMode: lambda.KafkaConsumptionMode.STREAM,
  // startingPosition: lambda.StartingPosition.LATEST,
}));
```

**ポイント:**
- `consumptionMode` は self-managed Kafka (`kafkaBootstrapServers` 指定) でのみ利用可能で、他のイベントソースで指定すると synth で失敗します。
- queue モードでは `startingPosition` / `startingPositionTimestamp` / 無限リトライ (`retryAttempts: -1`) を指定するとエラーになります。`maxBatchingWindow` も queue モードでは機能しないため、Lambda サービス側のデプロイ時バリデーションに委ねられます。
- `startingPosition` は `BaseStreamEventSourceProps` でオプショナルになりました。Kinesis / DynamoDB / MSK / self-managed Kafka の stream モードでは依然として synth 時に必須です。
- `KafkaConsumptionMode.of()` でカスタム値を渡した場合や未解決トークンは検証がスキップされます。

## バグ修正

### iam: インポートしたユーザー/グループのデフォルトポリシー名が stack-safe でない ([#38894](https://github.com/aws/aws-cdk/pull/38894))
- インポートされたユーザーまたはグループが作成するデフォルトのインラインポリシーは、ハードコードされた construct id (ユーザーは `'Policy'`、グループは `'DefaultPolicy'`) を使うため、ポリシー名がスタック内のパスのみに依存していました。同じプリンシパルを同じ construct id でインポートする 2 つのスタックがあると、同じ物理プリンシパル上で同じインラインポリシー名を使ってしまい、2 つ目のスタックが CloudFormation によって拒否される問題がありました。
- 新しい feature flag `@aws-cdk/aws-iam:importedUserAndGroupStackSafeDefaultPolicyName` (推奨値 `true`) を有効にすると、`Names.uniqueResourceName` で `stackName` を含む stack-safe な `policyName` が割り当てられるようになり、異なるスタックから同じユーザー/グループへ別々のインラインポリシーをアタッチできるようになります。
- 既存デプロイに適用する場合、同じプリンシパルをインポートするスタックは**まとめてデプロイ**する必要があります。最初のスタックが policy をリネームすると CloudFormation は旧名称のインラインポリシーを削除するため、未デプロイのスタックの grant が一時的に消える可能性があります。
- Logical ID は変わらず、`PolicyName` の変更は `Update requires: No interruption` のため in-place で更新されます。インポートされた role には元から対策済み (#23080) で変更ありません。

### core: 複数のシェル引数が未エスケープ ([#39688](https://github.com/aws/aws-cdk/pull/39688))
- CodeBuild / EC2 インスタンス等で、最終的にシェルコマンド行に渡される CDK プロパティの hygiene スイープを実施し、未エスケープの箇所をまとめて修正しました。

### core: `cloudformation-validate` を最新版へ更新 ([#39643](https://github.com/aws/aws-cdk/pull/39643))
- 新しい L1 プロパティに対する strict モードの `F3002` エラー (例: Lambda の `AcceleratorConfig` や `RuntimeConfig`) を解消するため、バンドルしている `@aws/cloudformation-validate` が最新版に更新されました。

### core: バンドル `minimatch` を 11.0.8 に更新 (CVE-2026-118764) ([#39595](https://github.com/aws/aws-cdk/pull/39595))
- セキュリティ脆弱性 CVE-2026-118764 に対処するため、バンドルしている `minimatch` を 11.0.8 に更新しました。

### core: アセットハッシュとシンボリックリンクの契約がドキュメント化されていない ([#39779](https://github.com/aws/aws-cdk/pull/39779))
- アセットハッシュの計算とシンボリックリンクの扱いに関する契約がコードコメント・ドキュメントに記述されるようになりました。

### awslint: `--quiet` が warning / skipped diagnostics で無視される ([#39790](https://github.com/aws/aws-cdk/pull/39790))
- `awslint` の `--quiet` フラグが warning および skipped 診断に対して効かず、出力を抑制できなかった問題を修正しました。

## 破壊的変更

L1 リソースは CloudFormation の公開 Resource Schema から自動生成されており、実状をより正確に反映するために今回以下の変更が含まれます。

### aws-bedrockagentcore: PaymentManager のプロパティ型変更 ([#39847](https://github.com/aws/aws-cdk/pull/39847), [#39788](https://github.com/aws/aws-cdk/pull/39788))

- `AWS::BedrockAgentCore::PaymentManager` の `AuthorizingClaimMatchValue` 型が削除され、`AuthorizingClaimMatchValueType` に置き換えられました。
- `AWS::BedrockAgentCore::PaymentManager` の `ClaimMatchValue` 型が削除され、`ClaimMatchValueType` に置き換えられました。
- `AWS::BedrockAgentCore::PaymentManager` の `CustomJWTAuthorizer` 型が削除され、`CustomJWTAuthorizerConfiguration` に置き換えられました。

**移行方法:**
- 旧型を使っているコードは、新しい `*Type` / `*Configuration` 型に置き換えてください。

### aws-servicecatalog: AcceptedPortfolioShare の Id 属性削除 ([#39847](https://github.com/aws/aws-cdk/pull/39847))

- `AWS::ServiceCatalog::AcceptedPortfolioShare` から `Id` 属性が削除されました。

**移行方法:**
- `acceptedPortfolioShare.attrId` を参照していた場合は削除し、CloudFormation の最新スキーマに沿って参照方法を変更してください。

## まとめ

Lambda Managed Instances での GPU アクセラレータ (`AcceleratorConfig`) と Customer-Managed Runtimes 対応 (`FunctionRuntimeConfig` mixin)、API Gateway のプロキシ `autoConfigurePathParameter`、EC2 の IPAM CIDR サブネット、RDS の CloudWatch メトリクスヘルパー、ELBv2 の RFC 9151 SSL ポリシーと正規表現リスナー条件、self-managed Kafka の queue 消費モードなど、幅広い L2 の機能追加が含まれる充実したリリースです。あわせて `core` では Docker bundling イメージの遅延ビルドによる synth 時間短縮や、構造化設計コンテキスト (MetadataContext) の埋め込みなどが追加され、日常的な開発体験の向上に寄与する改善が揃っています。L1 自動更新に伴う aws-bedrockagentcore / aws-servicecatalog の破壊的変更があるため、該当プロパティを利用中の場合はアップグレード前にご確認ください。
