## 概要

このリリースでは、EC2 のリージョナル NAT Gateway、Glue 6.0、Synthetics Canary の環境変数 KMS 暗号化などの新機能が追加されました。合わせて L1 CloudFormation リソース定義が更新され、`AWS::ServiceDiscovery::Instance` の主キー変更に伴う破壊的変更が含まれます。BedrockAgentCore Browser の `grantUse` 権限不足、`cdk synth` が Windows の cloud-placeholder で EISDIR を投げる問題、Lambda の Node.js バンドルが AllSigned ポリシー下で失敗する問題なども修正されています。

**リリース:** [v2.272.0](https://github.com/aws/aws-cdk/releases/tag/v2.272.0)

## 新機能

### EC2 のリージョナル NAT Gateway サポート ([#36538](https://github.com/aws/aws-cdk/pull/36538))

**この機能でできること:**
- 2025 年 11 月に AWS が対応した「リージョナル NAT Gateway」（単一の NAT Gateway が複数の AZ をカバーする構成）を L2 で指定できるようになりました。
- 新しい `NatProvider.regionalGateway()` スタティックメソッドが追加され、`RegionalNatGatewayProvider` によって `availabilityMode: 'regional'` の NAT Gateway を単一リソースとして作成できます。

**使用例:**

```typescript
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import { Duration } from 'aws-cdk-lib';

new ec2.Vpc(this, 'MyVpc', {
  // リージョナル NAT Gateway プロバイダーを指定
  // 複数 AZ があっても NAT Gateway は 1 つだけ作成される
  natGatewayProvider: ec2.NatProvider.regionalGateway({
    // 既存 EIP の allocationId を指定可能（省略時は新規作成）
    // allocationId: 'eipalloc-xxxxxxxxxxxxxxxxx',
    // あるいは EIP リソースを直接渡すこともできる
    // eip: new ec2.CfnEIP(this, 'MyEip'),
    // AZ 単位で EIP 割り当てを手動制御したい場合に利用
    // availabilityZoneAddresses: {
    //   'us-east-1a': { allocationId: 'eipalloc-aaa' },
    //   'us-east-1b': { allocationId: 'eipalloc-bbb' },
    // },
    // 強制的に IP が解放されるまでの最大待機時間
    maxDrainDuration: Duration.minutes(5),
  }),
});
```

**ポイント:**
- リージョナル NAT Gateway は AZ 数にかかわらず NAT Gateway リソースを 1 つだけ作成します（`determineNatGatewayCount()` は常に 1 を返す）。
- 既存 EIP を利用したい場合は `allocationId` もしくは `eip` オプションを使います。片方だけ指定できます。
- `availabilityZoneAddresses` を使うと、特定の AZ の EIP 割り当てを手動で指定できます。
- 詳細は [AWS のリリース発表](https://aws.amazon.com/about-aws/whats-new/2025/11/aws-nat-gateway-regional-availability/) および [NAT Gateway ユーザーガイド](https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateways-regional.html) を参照してください。

### Glue 6.0 サポート ([#38632](https://github.com/aws/aws-cdk/pull/38632))

**この機能でできること:**
- AWS Glue 6.0 のリリースに合わせて、`aws-cdk-lib/aws-glue` の `GlueVersion` に `V6_0` が追加されました。
- Glue モジュールが安定モジュールへ昇格済みであるため、`aws-cdk-lib` から直接利用できます。

**使用例:**

```typescript
import * as glue from 'aws-cdk-lib/aws-glue';
import * as s3 from 'aws-cdk-lib/aws-s3';

const scriptBucket = new s3.Bucket(this, 'ScriptBucket');

new glue.Job(this, 'MyGlueJob', {
  executable: glue.JobExecutable.pythonEtl({
    // Glue 6.0 ランタイムを指定（Iceberg v3 対応・値下げあり）
    glueVersion: glue.GlueVersion.V6_0,
    pythonVersion: glue.PythonVersion.THREE,
    script: glue.Code.fromBucket(scriptBucket, 'etl.py'),
  }),
});
```

**ポイント:**
- Glue 6.0 では Iceberg v3 への対応と値下げが行われています（[AWS 発表](https://aws.amazon.com/about-aws/whats-new/2026/08/aws-glue-6-0-price-reduction-iceberg-v3/) を参照）。
- `GlueVersion` の JSDoc リンクが Glue リリースノートへ更新されました。

### Synthetics Canary の環境変数 KMS 暗号化プロパティ追加 ([#38750](https://github.com/aws/aws-cdk/pull/38750))

**この機能でできること:**
- CloudWatch Synthetics の Canary が持つ `KmsKeyArn` プロパティ（Canary の Lambda 関数の環境変数を KMS カスタマーマネージドキーで暗号化する設定）を L2 から直接指定できるようになりました。
- これまでは L1 `CfnCanary` のエスケープハッチで設定する必要がありました。
- 既存の `artifactS3KmsKey`（S3 アーティファクトの暗号化）とは別の設定である点に注意してください。

**使用例:**

```typescript
import * as synthetics from 'aws-cdk-lib/aws-synthetics';
import * as kms from 'aws-cdk-lib/aws-kms';
import { Duration } from 'aws-cdk-lib';

const encryptionKey = new kms.Key(this, 'CanaryEnvKey');

new synthetics.Canary(this, 'MyCanary', {
  runtime: synthetics.Runtime.SYNTHETICS_NODEJS_PUPPETEER_7_0,
  test: synthetics.Test.custom({
    code: synthetics.Code.fromInline('exports.handler = async () => {};'),
    handler: 'index.handler',
  }),
  schedule: synthetics.Schedule.rate(Duration.minutes(5)),
  environmentVariables: {
    SECRET_URL: 'https://example.com/secret',
  },
  // 新しく追加された環境変数の暗号化キー
  // 未指定の場合は AWS 所有キーが使われる（既存挙動と互換）
  environmentEncryption: encryptionKey,
});
```

**ポイント:**
- プロパティ名・型・マッピングは `lambda.Function.environmentEncryption` と揃えられています（Canary 内部は Lambda として動作するため）。
- Canary の実行ロールには KMS 権限は不要です（Lambda がグラント経由で暗号化・復号を行う仕様）。
- スタック実行者には `kms:CreateGrant` / `kms:Encrypt` / `kms:Decrypt` / `kms:DescribeKey` の権限が必要です。同一スタック内で作成したキーならデフォルトキーポリシーで満たされます。
- 未指定時は CloudFormation テンプレート上の `KmsKeyArn` も出力されないため、既存のスタックには影響がありません。

### L1 CloudFormation リソース定義の更新 ([#38864](https://github.com/aws/aws-cdk/pull/38864))

**この機能でできること:**
- `@aws-cdk/aws-service-spec` の最新定義を取り込み、各サービスの L1（`CfnXxx`）リソースのプロパティ・属性・タグ情報・プライマリ識別子が最新 CloudFormation スキーマに合わせて更新されました。
- 代表的な追加例として、`AWS::ApplicationAutoScaling::ScalableTarget` に `Tags`、`AWS::AppStream::ImageBuilder` に `DisableIMDSV1` などが追加されています（詳細は PR を参照）。

**ポイント:**
- L1 の自動更新に伴い、`AWS::ServiceDiscovery::Instance` などプライマリ識別子変更に起因する破壊的変更が同時に含まれます（後述の「破壊的変更」セクション参照）。

## バグ修正

### BedrockAgentCore Browser の `grantUse` に `ConnectBrowserAutomationStream` が不足 ([#38657](https://github.com/aws/aws-cdk/pull/38657))

- `BrowserCustom.grantUse()` が付与する権限セット (`BROWSER_USE_PERMS`) に `bedrock-agentcore:ConnectBrowserAutomationStream` が含まれておらず、`StartBrowserSession` 自体は成功するものの、その後のオートメーションストリーム（Chrome DevTools Protocol 経由のブラウザ操作）接続で `403 Forbidden` となっていました。
- セッションは `READY` に到達しログにも IAM 由来の手がかりが残らないため、デバッグが困難な不具合でした。
- 修正により、`grantUse()` が `ConnectBrowserAutomationStream` を付与するようになり、エージェントが Browser を実際に操作できるようになりました。
- 権限はブラウザのリソース ARN (`arn:aws:bedrock-agentcore:<region>:<accountId>:browser-custom/<id>`) にスコープされています。
- なお、`ConnectBrowserLiveViewStream`（人間がライブで観察・引き継ぐための別エンドポイント）はエージェントの最小権限原則から外れるため `grantUse()` には含まれず、必要なら `grant()` 経由で付与する運用になっています。

### `cdk synth` が cloud-placeholder ディレクトリで EISDIR クラッシュ ([#38672](https://github.com/aws/aws-cdk/pull/38672))

- `aws-cdk-lib` v2.262.0 以降、`cdk.out` 配下に Windows のリパースポイント（例: OneDrive などの Windows クラウドファイルのプレースホルダー）が存在すると、`cdk synth` が `EISDIR: illegal operation on a directory, read` でクラッシュしていました。
- 原因は `collectFilePaths()` が `readdirSync({ withFileTypes: true })` の結果でエントリ種別を判定しており、後段の `hashFile` 側では `lstat` を使うため両者で判定が食い違い、ディレクトリに対して `readFileSync` を呼んでしまうケースがあったことです。
- 修正により、`collectFilePaths()` は `lstat()` が返す種別（`isFile()` または `isSymbolicLink()`）でゲートするようになり、Windows cloud-placeholder でも synth が落ちなくなりました。
- #38299 で修正されていた「実シンボリックリンクをディレクトリに向ける」ケースと矛盾しない形で動作します。

### Lambda の Node.js バンドルが AllSigned PowerShell 実行ポリシー下で失敗する問題 ([#38447](https://github.com/aws/aws-cdk/pull/38447))

- Windows でローカルバンドリングを実行すると、内部的に `powershell.exe -NoProfile -Command "& 'npm' 'ci'"` が呼ばれます。コマンド名が裸で渡されるため、PowerShell が `npm.ps1` シムを選択してしまうことがあり、`.ps1` は実行ポリシーの制約対象のため、`AllSigned`（`MachinePolicy` スコープで強制）な環境では `-ExecutionPolicy Bypass` でも回避できず失敗していました。
- 修正では `Get-Command <name> -CommandType Application` によって先に実行可能ファイル（`.cmd` / `.exe`）を解決してから呼び出すようになり、`.ps1` シムが選ばれなくなりました。
- 既存の対応（引数の個別クォートによるコマンドインジェクション対策、`.cmd` 直接 spawn ではなく PowerShell 経由にする `EINVAL` 対策 (#37412)）はそのまま維持されています。
- 挙動の差分として、実行ファイルが見つからない場合は spawn の失敗ではなく PowerShell の `CommandNotFoundException` として現れます（コマンド名はエラーメッセージに残ります）。

## 破壊的変更

### `AWS::ServiceDiscovery::Instance` の主キー変更 ([#38864](https://github.com/aws/aws-cdk/pull/38864))

L1 CloudFormation リソース定義の更新に伴い、`AWS::ServiceDiscovery::Instance` のプライマリ識別子が `ServiceId` と `InstanceId` の組み合わせに変更されました。これに合わせて `InstanceReference` が `serviceId` を必須プロパティとして要求するようになっています。

**変更前:**

```typescript
// InstanceReference に serviceId が無くても参照可能だった
const instanceRef: cloudformation.InstanceReference = {
  instanceId: 'my-instance-id',
};
```

**変更後:**

```typescript
// serviceId が必須になった
const instanceRef: cloudformation.InstanceReference = {
  serviceId: 'my-service-id',
  instanceId: 'my-instance-id',
};
```

**移行方法:**
- `AWS::ServiceDiscovery::Instance` を参照している箇所で `InstanceReference` を構築している場合、`serviceId` を併せて指定するようコードを更新してください。
- CloudFormation の実態（primary identifier の変更）に合わせた変更であり、L1 の型のみ影響する破壊的変更です。L2 側の `Service` / `IService` ベースの API を使っている場合は原則影響しません。

## まとめ

リージョナル NAT Gateway、Glue 6.0、Synthetics Canary の環境変数暗号化と、実用的な L2 新機能が揃ったリリースです。合わせて L1 自動更新に伴う ServiceDiscovery の破壊的変更、BedrockAgentCore Browser の権限不足修正、Windows 環境での synth / Lambda バンドル問題の修正など、環境依存の落とし穴に効く修正が含まれています。
