## 概要

AWS CDK v2.267.0 は、Backup の Backup Index、SQS スケールイン用の合計メトリック、Lambda コンテナイメージ関数への SnapStart 対応といった機能追加に加え、大規模スタックでの `addDependency` パフォーマンス改善、`stack.availabilityZones` の値の安定化、DynamoDB `TableV2` の grant バグ修正、S3 Bucket Deployment のデフォルトメモリ 128MB → 1024MB 引き上げなど、実運用で効いてくる修正が多数入ったリリースです。破壊的変更として Kinesis Data Firehose の `timeZone` (旧 `customTimeZone`) が synth 時にサポート外の値を弾くようになりました。Alpha モジュールでは `glue-alpha` に GA 前 API レビュー由来の破壊的変更 (`S3Table` storage/encryption と Schema `Type` の value object 化)、`msk-alpha` の Kafka 4.2 対応、`s3tables-alpha` のストレージクラス設定サポートが含まれます。

**リリース:** [v2.267.0](https://github.com/aws/aws-cdk/releases/tag/v2.267.0)

## 新機能

### `backup`: `BackupPlanRule` に `indexActions` を追加 ([#34051](https://github.com/aws/aws-cdk/pull/34051))

**この機能でできること:**

- AWS Backup の Backup Index (バックアップの検索を可能にする機能) を、`BackupPlanRule` から宣言的に有効化できるようになりました。従来はこの設定を CDK コードから指定する手段がなく、CFN L1 に落ちる必要がありました。
- 現在、AWS Backup 側では 1 つの `BackupRule` あたり最大 1 個の `IndexAction` しか設定できません。対象リソースタイプ (`resourceTypes`) は現状 `S3` / `EBS` の 2 種類が組み込みで用意されており、AWS 側で将来追加された値も `new IndexActionResourceType('EFS')` のようにコンストラクタ経由で先行利用できます。

**使用例:**

```typescript
import * as cdk from 'aws-cdk-lib';
import * as backup from 'aws-cdk-lib/aws-backup';
import { Construct } from 'constructs';

export class BackupIndexStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    new backup.BackupPlan(this, 'Plan', {
      backupPlanRules: [
        new backup.BackupPlanRule({
          // 通常のバックアップ設定 (省略可能なプロパティは適宜)
          ruleName: 'daily',
          scheduleExpression: cdk.aws_events.Schedule.cron({ hour: '3', minute: '0' }),

          // ★ 新規追加: Backup Index を有効化する
          //   1 rule あたり最大 1 個 の IndexAction のみ設定可
          indexActions: [
            {
              // 対象リソースタイプ (S3 / EBS などから 1 つ以上)
              resourceTypes: [
                backup.IndexActionResourceType.S3,
                backup.IndexActionResourceType.EBS,
              ],
            },
          ],
        }),
      ],
    });
  }
}
```

**ポイント:**

- `resourceTypes` は空配列にできない設計 (指定した時点で index を作りに行く扱い) です。使わない場合は `indexActions` プロパティ自体を渡さないでください (`@default - no index actions`)。
- `IndexActionResourceType` は enum ではなくクラスで、静的な `S3` / `EBS` に加え、コンストラクタで任意の文字列を渡せる「未来のリソースタイプ用エスケープハッチ」も用意されています。

### `bedrockagentcore`: `AgentRuntime` に `manageDeliveryResourcePolicy` opt-out を追加 ([#38372](https://github.com/aws/aws-cdk/pull/38372))

**この機能でできること:**

- Bedrock AgentCore Runtime のオブザーバビリティ設定を有効化する際、CDK は付随して `AWS::Logs::ResourcePolicy` と `AWS::XRay::ResourcePolicy` を自動生成します。しかしこれらリソースポリシーはアカウント / リージョン単位の「クォータ枠」を消費します (CloudWatch Logs は 10 枠、X-Ray はさらに少ない)。多数の AgentCore Runtime を 1 アカウントに立てると簡単に上限を突破してしまう問題がありました。
- 新プロパティ `manageDeliveryResourcePolicy` (デフォルト `true` = 従来通り) を `false` にすることで、CDK 側でのリソースポリシー作成をスキップしつつ、Delivery Source / Destination / Delivery 本体は引き続き構成できます。同一アカウント内の `/aws/vendedlogs/*` への配信では、ログ配信サービスリンクロールが書き込み権限を担保するので、明示的なリソースポリシーは不要です。

**使用例:**

```typescript
import * as cdk from 'aws-cdk-lib';
import * as bedrockagentcore from 'aws-cdk-lib/aws-bedrockagentcore';
import { Construct } from 'constructs';

export class AgentRuntimeStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    new bedrockagentcore.Runtime(this, 'Runtime', {
      // ... 他の必須プロパティ ...

      // オブザーバビリティ設定
      observability: {
        // ★ アカウント内で AgentCore Runtime を多数立てるユースケースでは
        //   false にしてクォータ消費を回避 (同一アカウントの /aws/vendedlogs/*
        //   への配信であればサービスリンクロール経由で権限が付くため問題なし)
        manageDeliveryResourcePolicy: false,
      },
    });
  }
}
```

**ポイント:**

- クロスアカウントでのログ配信など、`vendedlogs` 経由でない・サービスリンクロールが効かないケースでは、リソースポリシーが必要になるため `true` のままにしてください (もしくは自前で `AWS::Logs::ResourcePolicy` などを別途管理)。
- 既存コードは何もしなくても従来通り (`true` 相当) の挙動になり、後方互換です。

### `core`: `Size` オブジェクトが正しく文字列化されるように ([#38662](https://github.com/aws/aws-cdk/pull/38662))

**この機能でできること:**

- CDK の `Size` オブジェクト (例: `Size.mebibytes(512)`) をエラーメッセージなどで文字列に変換した際、これまで `[object Object]` が出力されていました。デバッグ時に単位や数値がまったく分からず不便でした。
- 本リリース以降は、`Size` の `toString()` が意味のある表現 (例: `Size#{ amount: 512, unit: "mebibytes" }` 相当) を返すようになり、ログや例外メッセージからそのままサイズを読み取れるようになります。

**使用例:**

```typescript
import { Size } from 'aws-cdk-lib';

const memory = Size.mebibytes(512);
console.log(`configured memory: ${memory}`);
// 従来: configured memory: [object Object]
// 修正後: 数値と単位が読める形で出力される
```

**ポイント:**

- 挙動 (合成される CloudFormation テンプレート) には影響しません。純粋にデバッグ用の可読性向上です。

### `sqs`: `metricApproximateNumberOfMessagesOutstanding` を追加 ([#38661](https://github.com/aws/aws-cdk/pull/38661))

**この機能でできること:**

- SQS キューを消費する ECS / EC2 コンシューマーをオートスケールする際、単純に `ApproximateNumberOfMessagesVisible` (未受信メッセージ数) だけを見ると、受信済みかつ処理中 (visibility timeout 内、`NotVisible` 状態) のメッセージが「0 に見える」ため、まだ処理中の消費者を殺してしまい重複処理や取りこぼしを起こす、というのが典型的な落とし穴です。
- スケールインで安全に使えるシグナルは `Visible + NotVisible` (= 「まだ完了していないメッセージ数」) の合計ですが、これまでは `MathExpression` を手で組む必要がありました。本 PR で `IQueue` に `metricApproximateNumberOfMessagesOutstanding(props?)` が追加され、この合計を `MathExpression` として一発で取得できます。

**使用例:**

```typescript
import * as cdk from 'aws-cdk-lib';
import * as sqs from 'aws-cdk-lib/aws-sqs';
import * as cloudwatch from 'aws-cdk-lib/aws-cloudwatch';
import { Construct } from 'constructs';

export class SqsScaleStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    const queue = new sqs.Queue(this, 'Queue');

    // Visible + NotVisible の合計を返す MathExpression
    //   MathExpression なので createAlarm() / with() がそのまま使える
    const outstanding = queue.metricApproximateNumberOfMessagesOutstanding({
      // statistic / period などは MetricOptions 経由で伝播
      period: cdk.Duration.minutes(1),
      statistic: 'Sum',
    });

    // スケールインをこのメトリクスに紐付けて、処理中メッセージがある間は
    // 「消費者ゼロ」まで縮退させないポリシーを組める
    outstanding.createAlarm(this, 'ScaleInAlarm', {
      threshold: 0,
      comparisonOperator: cloudwatch.ComparisonOperator.LESS_THAN_OR_EQUAL_TO_THRESHOLD,
      evaluationPeriods: 5,
    });
  }
}
```

**ポイント:**

- `ApproximateNumberOfMessagesDelayed` は意図的に加算されていません。遅延メッセージは「まだ受信さえできない」状態のため、これを含めるとスケールインが遅延キューの残件に引きずられて永遠に起きなくなるためです。
- スケールアウト側は従来通り `ApproximateNumberOfMessagesVisible` / `metricApproximateNumberOfMessagesVisible()` を使うのが推奨です (スケールアウトとスケールインで別メトリクスを使うのが SQS ワーカーの定石)。

### `assets`: `SymlinkFollowMode.BLOCK_EXTERNAL` でバンドル時にエラーを投げるように ([#38506](https://github.com/aws/aws-cdk/pull/38506))

- あわせて外部シンボリックリンクを含む出力を `BLOCK_EXTERNAL` モードで許してしまわないよう ([#38665](https://github.com/aws/aws-cdk/pull/38665))、ディレクトリバンドリング出力のシンボリックリンクも同モードで拒絶されます。

### `bedrockagentcore`: ブラウザ録画バケットの grant を最小権限化 ([#38604](https://github.com/aws/aws-cdk/pull/38604))

- `BrowserCustom` で S3 セッション録画を設定した際、ブラウザ実行ロールに対して録画バケットに `bucket.grantReadWrite` (S3 の約 50 個のアクション、バケット全体への Read/Write/Delete) が付与されていました。これはセッション録画の実挙動に照らして明らかに過剰でした。
- 修正後は、実際に録画機能が使うアクションのみ、かつリソーススコープも `bucket/prefix/*` (録画プレフィックス配下のオブジェクトのみ) に絞られます。
  - 付与アクション: `s3:PutObject` / `s3:ListMultipartUploadParts` / `s3:AbortMultipartUpload`
  - リソース: プレフィックスが具体的な文字列なら末尾スラッシュを正規化して `prefix/*`、トークンならそのまま `prefix*` で残す挙動
- 既存デプロイに対しても、次回デプロイで生成されるポリシーが縮小するだけで挙動差はありません (実行時に必要な権限は全て保たれています)。

### `cloudfront-origins`: `readTimeout` / `keepaliveTimeout` が有効な値を拒否する問題を修正 ([#38432](https://github.com/aws/aws-cdk/pull/38432))

- `HttpOrigin` / `VpcOrigin` / `FunctionUrlOrigin` / `RestApiOrigin` の `readTimeout` / `keepaliveTimeout` に対し、CDK が「180 秒」というハードコードされた上限を持っていました。しかし CloudFront のドキュメント上のクォータは実際には以下のように異なります。
  - `readTimeout` (Response timeout per origin): デフォルト `1-120 秒`、クォータ緩和で上限引き上げ可能
  - `keepaliveTimeout` (Keep-alive timeout per origin): `1-300 秒` (デフォルトクォータの範囲でそもそも 300 秒までいける)
- そのため、`keepaliveTimeout: 200` のような "デフォルトクォータの範囲で普通に使える値" が synth 時に弾かれる、あるいはクォータ緩和済みの値でも指定できないという不整合が起きていました。
- 修正では 4 つの L2 で上限のハードコードを撤廃し、下限 1 秒 / 整数秒である制約は維持しつつ、クォータ超過は CloudFront 側のデプロイ時エラーに委ねる形になりました。JSDoc もそれぞれ正しいクォータ表記に更新されています。

### `core`: パフォーマンスカウンタのメモリ使用量削減 ([#38620](https://github.com/aws/aws-cdk/pull/38620))

- CDK のパフォーマンスカウンタが Node.js の `perf_hooks` を利用して個々のエントリをグローバル配列に積んでいたため、大規模アプリでは GC 負荷が肥大化し、synth に 30 分以上の追加オーバーヘッドが乗るというレポートがありました。
- 結局最終的に必要なのは集計値だけなので、収集時点で pre-aggregate する実装に切り替え、`perf_hooks` の外部 API 互換は捨てました。大規模アプリの synth 時間が改善されます。

### `core`: `stack.node.addDependency` が大規模スタックで極端に遅くなる問題 ([#38597](https://github.com/aws/aws-cdk/pull/38597))

- `source.node.addDependency(target)` は、`source` 配下と `target` 配下のリソースをまず総当たり (デカルト積) で展開してから 1 対 1 の依存を張る実装になっていました。しかし `source` / `target` が Stack (数百リソースを持ちうる) のケースでは、最終的に単一の Stack 間依存に集約されるだけなのに、途中で `O(source × target)` の作業が発生してしまい、実測では二次を超えるオーダーで遅くなることがありました (#38522 も同根)。
- 修正では、依存対象がスタック単位で解決可能な場合はデカルト積展開を行わず、直接スタック間依存を張るように内部フローを整理しました。同スタック内のリソース間依存は従来通りの展開ルートを通ります。
- 併せて内部 API の命名も整理: 従来の `stack.addDependency` / `resource.addDependency` は「即時に CFN DependsOn を張る」意味だったところ、`stack.node.addDependency` (synth 時に解決される construct レベル依存) と字面が近くて混乱していたため、直接系は `stack.addStackDependency` / `resource.addResourceDependency` にリネームされました。挙動は変わりません。

### `core`: バリデーションプラグインチェックのオーバーヘッド削減 ([#38619](https://github.com/aws/aws-cdk/pull/38619))

- 修正では synthesis あたり 1 回だけ検査するように簡略化し (エラーメッセージは若干粗くなる代わり)、trusted plugin ではスキップされるようになりました。

### `dynamodb`: `TableV2.grants.*Data` がインデックスリソースを含めない問題 ([#37892](https://github.com/aws/aws-cdk/pull/37892))

- `TableV2` を作成した後に `addGlobalSecondaryIndex` / `addLocalSecondaryIndex` で GSI/LSI を追加し、その後 `table.grants.grantReadData(role)` 等で権限付与すると、生成される IAM ポリシーの `Resource` から `${tableArn}/index/*` が抜けてしまい、実際にインデックスに対するクエリが AccessDenied で失敗するというバグがありました。
- 根本原因は、`TableV2` コンストラクタ末尾で `TableGrants` を組み立てる際に `hasIndex: this.hasIndex` を "その時点の値" (= まだ index 追加前なので `false`) でキャプチャしていたことです。旧 `Table` (v1) の `grant*Data` はもともと `Lazy.string` で synth 時に解決していたため、正しく動作していました。
- 修正では `TableV2` 側から `hasIndex` を渡すのをやめ、`TableGrants.arnForIndex` の Lazy に判定を委ねるようにしました。コンストラクション後に GSI/LSI を追加する自然なパターンでも `/index/*` が正しく含まれるようになります。

### `dynamodb`: `TableV2MultiAccountReplica` がトークン化 ARN を持つインポートテーブルを拒否する問題 ([#38365](https://github.com/aws/aws-cdk/pull/38365))

- `TableV2MultiAccountReplica` の `validateMultiAccountReplica` は、ARN の一部でもトークンなら ARN パースをスキップしてスタック環境にフォールバックする実装でした。しかしテーブル名部分だけがトークン化されている (アカウント/リージョンは実値) 部分的トークン ARN では、スタックが常に same-account に見えてしまい `MultiAccountReplicaMustBeDifferentAccount` が誤って発火していました。
- 修正では「ARN 全体が単一のトークンで実部が全く無いケース」だけをスキップ対象に絞り、それ以外は `splitArn` に通すようになりました (splitArn 内でも要素ごとに `Token.isUnresolved` を持っているので、部分トークンは適切に個別スキップされます)。挙動変化は false-positive を消すのみで、既存の正当な検証は維持されます。

### `dynamodb`: `TableV2` で `TableGrantsProps` の deprecation 警告が出る問題 ([#38399](https://github.com/aws/aws-cdk/pull/38399))

- `TableV2` を使うと (`DynamoEventSource` などから内部的に `grantStreamRead` などが呼ばれた際に) 、CDK 内部で明示的 deprecated な `TableGrantsProps.policyResource` / `encryptedResource` が組み立てられ、synth 時に以下のような警告がユーザー側では抑制できない形で出ていました。
  ```
  [WARNING] aws-cdk-lib.aws_dynamodb.TableGrantsProps#policyResource is deprecated.
  [WARNING] aws-cdk-lib.aws_dynamodb.TableGrantsProps#encryptedResource is deprecated.
  ```
- `TableV2` (経由の `CfnGlobalTable`) は既に `IEncryptedResource` / `IResourceWithPolicyV2` を実装しているため、明示指定を外しても IAM 側の自動発見で正しく解決できます。修正では `TableV2` / `TableReplicaV2` のコンストラクタから deprecated プロパティの明示指定を除去しました。挙動変化は警告が消えるだけです。

### `ec2`: `NatInstanceProvider` / `NatInstanceProviderV2` が常に `keyName` の deprecation 警告を出す問題 ([#38347](https://github.com/aws/aws-cdk/pull/38347))

- `NatProvider.instance()` / `NatProvider.instanceV2()` を使って VPC を作ると、`keyName` を指定していない場合でも毎回 `[WARNING] aws-cdk-lib.aws_ec2.InstanceProps#keyName is deprecated.` が synth 時に出続けていました。
- 原因は、内部で常に `keyName: this.props.keyName` を props オブジェクトに書き込んでおり、jsii の deprecation 警告が「プロパティキーが存在するか (`"keyName" in props`)」で発火するため、値が `undefined` でも警告が出てしまうというものでした。
- 修正では `AutoScalingGroup` で既に採用されているパターンに揃え、`keyName` が指定された時のみキーを混ぜ込むように変更されています。ユーザー側の使い方は変わりません。

### `kinesisfirehose`: `S3BucketProps` の `timeZone` に synth 時バリデーションを追加 ([#38514](https://github.com/aws/aws-cdk/pull/38514)) 【破壊的変更】

- Firehose の S3 送信先で `timeZone` (`CustomTimeZone`) にサポート外の値を渡した場合、これまで synth は通過して CloudFormation デプロイ時に初めて `AWS Kinesis Firehose delivery stream, the supported IANA time zone formats are non-3-letter identifiers` などのエラーで落ちていました。
- 修正で `createTimezoneName` に synth 時バリデーションが追加され、サービスが受け付けない値は synth 時に `ValidationError` で失敗します。以下の値が新たに拒否されるようになりました。
  - 3 文字略号 (`EST`, `PST` 等)
  - `Etc/UTC`, `Etc/GMT`, `Factory`
  - サービス正規表現 `[a-zA-Z/_]+` から外れる文字を含む値
- 有効なのは `UTC` および標準 IANA 識別子 (例: `America/New_York`, `Asia/Tokyo`) で、これらの値を使っていた場合は影響ありません。allow list 全てを CDK 側で持つと保守コストが高いため、あくまで best-effort な synth 時バリデーションで、well-formed だが存在しない `America/Foo` のような値はまだデプロイ時エラー扱いになります。

**変更前:**

```typescript
import * as firehose from 'aws-cdk-lib/aws-kinesisfirehose';

new firehose.S3Bucket(bucket, {
  timeZone: 'EST', // 3 文字略号: 従来は synth を通過し deploy で失敗
});
```

**変更後:**

```typescript
import * as firehose from 'aws-cdk-lib/aws-kinesisfirehose';

new firehose.S3Bucket(bucket, {
  // 標準 IANA 識別子 or 'UTC' を指定する
  timeZone: 'America/New_York',
});
```

**移行方法:**

- 3 文字略号 (`EST`, `PST` 等) を使っていた場合は `America/New_York` / `America/Los_Angeles` 等の Region/City 形式に置き換えてください。`Etc/UTC` を使っていた場合は `UTC` に。

### `lambda`: コンテナイメージ関数で SnapStart を許可 ([#38680](https://github.com/aws/aws-cdk/pull/38680))

- Lambda コンテナイメージ (OCI) デプロイでの SnapStart 対応が Lambda 側で再開されたため、CDK 側でもコンテナイメージ関数に対する SnapStart 指定を許可するように戻されました (先行して #38265 で入り、リリースタイミング調整のため #38281 で一時 revert されていた変更のリロール)。
- コンテナイメージ (`FROM_IMAGE`) のケースでは、CDK は client-side でイメージ内ランタイムを検査できないため、ランタイム対象性のチェックは Lambda 側に委ねる形になっています (デプロイ時に不適格ならサービス側が弾く)。EFS / ephemeral storage (>512 MiB) / tenant-isolation の制約チェックは従来通り synth 時に効きます。

**使用例:**

```typescript
import * as cdk from 'aws-cdk-lib';
import * as lambda from 'aws-cdk-lib/aws-lambda';
import { Construct } from 'constructs';

export class SnapStartContainerStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    const fn = new lambda.DockerImageFunction(this, 'Fn', {
      code: lambda.DockerImageCode.fromImageAsset('./docker'),
      // コンテナイメージ関数でも SnapStart を有効化できるように
      snapStart: lambda.SnapStartConf.ON_PUBLISHED_VERSIONS,
    });

    fn.currentVersion; // SnapStart はバージョン発行と併用
  }
}
```

### `s3-deployment`: BucketDeployment Lambda のデフォルトメモリを 128MB → 1024MB に ([#35501](https://github.com/aws/aws-cdk/pull/35501)) 【実質的な破壊的変更 (コスト/挙動)】

### `stepfunctions-tasks`: `EvaluateExpression` の JSONPath を値ルックアップで解決 ([#38682](https://github.com/aws/aws-cdk/pull/38682))

- `EvaluateExpression` は生成 Lambda 上で JavaScript 式を評価するタスクで、`$.a` のような JSONPath トークンで実行ステートの値を参照できます。従来実装では単純文字列置換に近い挙動により、重なる path (`$.a` と `$.ab`、`$.a` と `$.a.b`) や multi-statement 式で解決が破綻するエッジケースがありました。

- 加えて、synth 時に「文字列/テンプレートリテラルの生テキストに JSONPath を書いた誤用 (例: `` `total: $.n` `` : 本来は `` `total: ${$.n}` ``)」を検出し、synth 時に fail-fast するようになりました。これはドキュメント外の使い方で、feature flag は用意されていません。

### `stack.availabilityZones` が不安定な文字列を返す問題を修正 ([#38580](https://github.com/aws/aws-cdk/pull/38580))

### `glue-alpha`: `Connection` に型付き `secret` を追加 ([#38585](https://github.com/aws/aws-cdk/pull/38585))

**この機能でできること:**

- Glue `Connection` の認証情報は、これまで free-form な `properties` マップ (=平文で CloudFormation テンプレートに埋め込まれる) にしか書けず、synth 時警告があるだけの状態でした。これは "最短経路の書き方が平文シークレットを Template に露出させる" という嫌な導線でした。
- 型付き `secret` プロパティ (`ISecretRef` 型) が追加され、指定した Secrets Manager のシークレットを Connection の `SECRET_ID` プロパティ経由で Glue に読ませる (=実際のシークレット値はテンプレートに出ない) 形で受け取れるようになりました。`properties` に `SECRET_ID` を書きながら同時に `secret` を渡すと synth 時に例外になります。

**使用例:**

```typescript
import * as glue from '@aws-cdk/aws-glue-alpha';
import * as secretsmanager from 'aws-cdk-lib/aws-secretsmanager';

declare const dbSecret: secretsmanager.ISecret;

new glue.Connection(this, 'Conn', {
  type: glue.ConnectionType.JDBC,
  properties: {
    JDBC_CONNECTION_URL: 'jdbc:mysql://host:3306/db',
    JDBC_ENFORCE_SSL: 'false',
  },
  // ★ 平文キー・シークレットを書かない。SECRET_ID 経由で Glue に読ませる
  secret: dbSecret,
});
```

**ポイント:**

- 型は `ISecretRef` を採用しています (`ISecret extends ISecretRef`)。これは awslint の `prefer-ref-interface` ルールに揃えるためで、Secrets Manager L2 のフル surface をこのモジュール型閉包に持ち込むのを避ける狙いです。既存の `ISecret` インスタンスはそのまま渡せます。
- `properties` 自体は残っていて free-form エスケープハッチとして使えるので、後方互換に影響はありません (併記時のみ synth 例外)。

### `glue-alpha`: `Connection` に `subnet selection` を追加 ([#38561](https://github.com/aws/aws-cdk/pull/38561))

**この機能でできること:**

- 従来ドキュメント上では VPC + サブネット選択が指定できるとされていたにも関わらず、実際の API にサブネット選択のプロパティが存在せず、意図されていた挙動を利用できませんでした。実装が追加され、他コンストラクトと同様の `vpc` + `subnetSelection` パターンが使えます。

```typescript
});
```

### `glue-alpha`: `S3Table` のストレージ/暗号化を value object に ([#38591](https://github.com/aws/aws-cdk/pull/38591)) 【破壊的変更】

**この機能でできること:**

- `S3Table` の `bucket` / `encryption` / `encryptionKey` は組み合わせによって「throw」「silent-drop」「s3 側で謎エラー」が入り乱れる状態でした。`encryption` enum も「バケットの SSE」と「テーブル側のクライアントサイド暗号化」を同じ列挙で扱っていて意味論が混ざっていました。
- これらを撤去して、`storage` (バケットの所有権と SSE) と `clientSideEncryption` (テーブル側のクライアントサイド暗号化) という直交する 2 つの value object に分離しました。不正状態はコンパイル時に表現不可能になります。あわせて `TableEncryption` enum と deprecated だった `Table` / `TableProps` (無利用) は削除されました。

**変更前:**

```typescript
import * as glue from '@aws-cdk/aws-glue-alpha';

new glue.S3Table(this, 'MyTable', {
  bucket: myBucket,
  encryption: glue.TableEncryption.KMS,
  encryptionKey: sseKey,
  // ...
});
```

**変更後:**

```typescript
import * as glue from '@aws-cdk/aws-glue-alpha';
import * as kms from 'aws-cdk-lib/aws-kms';

declare const sseKey: kms.IKey;
declare const cmsKey: kms.IKey;

new glue.S3Table(this, 'MyTable', {
  // ケース1: CDK にバケットを作らせ、SSE-KMS を自分の KMS キーで指定
  storage: glue.S3TableStorage.managedBucket(glue.S3TableEncryption.kms(sseKey)),

  // ケース2 (BYO bucket): 既存バケットを使う。ここで別に暗号化を渡すのは不正なので API 上表現できない
  //   storage: glue.S3TableStorage.fromBucket(myBucket),

  // 直交する概念として、テーブル側クライアントサイド暗号化キーを別途指定
  clientSideEncryption: glue.TableClientSideEncryption.kms(cmsKey),
});
```

**移行方法:**

- `bucket` を渡していた場合 → `storage: glue.S3TableStorage.fromBucket(bucket)` に置き換え。この形では `encryption` / `encryptionKey` は API 上受け付けなくなります (バケット自身の暗号化を使う)。
- `bucket` を渡していない場合 (CDK にバケットを作らせるパターン) → `storage: glue.S3TableStorage.managedBucket(glue.S3TableEncryption.kms(key?))` (キー省略時は新規生成) または `managedBucket(glue.S3TableEncryption.s3Managed())` に置き換え。
- クライアントサイド暗号化 (旧 `TableEncryption.CLIENT_SIDE_KMS`) は `clientSideEncryption: glue.TableClientSideEncryption.kms(key?)` に。
- `S3Table.encryption` / `encryptionKey` プロパティは削除。クライアントサイドキーは `clientSideEncryptionKey`、SSE キーは `bucket.encryptionKey` を参照してください。

### `glue-alpha`: Schema `Type` を opaque クラス化 & `StorageParameter` の型強化 ([#38592](https://github.com/aws/aws-cdk/pull/38592)) 【破壊的変更】

**この機能でできること:**

- Glue テーブルのカラム型 `Type` はこれまで `{ isPrimitive, inputString }` を持つオープンな interface で、`Schema` ファクトリーを介さずに手書きインスタンスを作れてしまう「無管理のエスケープハッチ」になっていました。修正で `Type` は opaque クラス化され、生成方法は `Schema` ファクトリーか、明示的なエスケープハッチ `Schema.custom(inputString, isPrimitive?)` のいずれかのみに絞られました。
- `Schema.decimal(precision, scale)` の `precision` (1-38) / `scale` (0..precision) 範囲チェックも追加 (`char` / `varchar` に既にあった範囲チェックと合わせる形)。
- `StorageParameter` の緩い primitives も strict 化: `custom(key, value)` の `value` は `any` から `string` に、`writeKmsKeyId(keyId: string)` は `writeKmsKeyId(key: kms.IKey)` に変更 (中で `key.keyId` をレンダー)。

**変更前:**

```typescript
import * as glue from '@aws-cdk/aws-glue-alpha';

// 手書きの型リテラル (もう使えない)
const t: glue.Type = { isPrimitive: true, inputString: 'MY_WEIRD_TYPE' };

glue.StorageParameter.custom('some_key', 42);       // number 渡し
glue.StorageParameter.writeKmsKeyId('my-key-id');   // 生 keyId 渡し
```

**変更後:**

```typescript
import * as glue from '@aws-cdk/aws-glue-alpha';
import * as kms from 'aws-cdk-lib/aws-kms';

declare const key: kms.IKey;

// ファクトリー経由 or Schema.custom を使う
const t1 = glue.Schema.INTEGER;
const t2 = glue.Schema.decimal(10, 2); // precision/scale の範囲もチェックされる
const t3 = glue.Schema.custom('MY_WEIRD_TYPE', /* isPrimitive= */ true);

glue.StorageParameter.custom('some_key', '42');      // string 化して渡す
glue.StorageParameter.writeKmsKeyId(key);            // kms.IKey を渡す
```

**移行方法:**

- 手書きの `Type` リテラルはすべて `Schema.*` ファクトリーか `Schema.custom(...)` に置き換えてください。
- `StorageParameter.custom(key, value)` の `value` は文字列化。
- `StorageParameter.writeKmsKeyId` に生の keyId を渡していた箇所は `kms.Key.fromKeyArn` 等で `IKey` を取り直して渡し替えてください。

## 破壊的変更まとめ

このリリースには以下の破壊的変更があります (詳細は各セクション参照)。

- **`kinesisfirehose`**: `S3Bucket` destination の `timeZone` にサポート外の値を渡すと、synth 時 `ValidationError` になります。3 文字略号 / `Etc/UTC` / `Etc/GMT` / `Factory` / `[a-zA-Z/_]+` から外れる文字を含む値は、標準 IANA 識別子 or `UTC` に置き換えてください。
- **`s3-deployment`** (実質的な挙動変化): `BucketDeployment` Custom Resource Lambda のデフォルトメモリが 128MB → 1024MB に。旧挙動に固定したい場合は `memoryLimit: 128` を明示指定してください。
- **Alpha - `glue-alpha`**: `S3Table` の `bucket` / `encryption` / `encryptionKey` が撤去され、`storage` / `clientSideEncryption` 値オブジェクトに置換。`TableEncryption` enum と deprecated `Table` / `TableProps` も削除。移行例は該当セクション参照。
- **Alpha - `glue-alpha`**: Schema `Type` が opaque クラス化。手書きリテラル (`{ isPrimitive, inputString }`) から `Schema.*` ファクトリー or `Schema.custom(...)` に移行してください。`StorageParameter.custom(key, value)` の `value` は `string` に、`StorageParameter.writeKmsKeyId` は `kms.IKey` を受け取るように変更。

## まとめ

v2.267.0 は、Backup Index / SQS の合計残数メトリック / Lambda コンテナ SnapStart 等の "使えるもの" 追加に加え、大規模スタックの `addDependency` パフォーマンス改善、`stack.availabilityZones` の値安定化、DynamoDB `TableV2` grant バグ修正、S3 Bucket Deployment のデフォルトメモリ大幅引き上げなど、実運用の痛点にストレートに効く修正が多く含まれるリリースです。Firehose `timeZone` の synth 時バリデーション強化 (破壊的変更) と、`glue-alpha` の GA 前 API リファクタ (`S3Table` storage/encryption と Schema `Type` の value object 化) は影響範囲が大きいので、該当機能を利用中のユーザーはアップグレード前に必ず変更内容を確認してください。
