## 概要

このリリースでは、CloudFront の Origin Access Control に Amazon S3 Multi-Region Access Point や Lambda Web Function Origin で必要となる `sigv4a` / `always-amz-auth` 署名のサポートが追加されました。また、CodeBuild の新しいビルドイメージ、Nested Stack での construct と CloudFormation リソースのトレース、API Gateway Stage のドリフト、Step Functions デフォルト IAM ロールの confused deputy 対策などの修正も行われています。Alpha モジュールでは、Bedrock Knowledge Base 向けの `VectorKnowledgeBase` L2 コンストラクトが追加されています。CloudFormation の L1 リソース定義の更新に伴う複数の破壊的変更にも注意が必要です。

**リリース:** [v2.274.0](https://github.com/aws/aws-cdk/releases/tag/v2.274.0)

## 新機能

### CloudFront: Origin Access Control に sigv4a 署名プロトコルを追加 ([#38629](https://github.com/aws/aws-cdk/pull/38629))

**この機能でできること:**
- CloudFront の Origin Access Control (OAC) で `sigv4a` 署名プロトコルがサポートされました。これは S3 Multi-Region Access Point をオリジンとして使用する際に必要な設定です。
- 新しく `SigningProtocol.SIGV4A` と、ドキュメントで推奨される組み合わせである `Signing.SIGV4A_ALWAYS` が追加されています。

**使用例:**

```typescript
import * as cloudfront from 'aws-cdk-lib/aws-cloudfront';

// S3 Multi-Region Access Point 向けの OAC
const oac = new cloudfront.S3OriginAccessControl(this, 'MrapOac', {
  // 新しく追加された static: sigv4a + always の組み合わせ
  signing: cloudfront.Signing.SIGV4A_ALWAYS,
});

// 任意の組み合わせを直接指定することも可能
const customSigning = new cloudfront.Signing({
  protocol: cloudfront.SigningProtocol.SIGV4A,
  behavior: cloudfront.SigningBehavior.ALWAYS,
});
```

**ポイント:**
- `S3MrapOrigin` 自体は今回の PR には含まれておらず、別途 Issue [#38627](https://github.com/aws/aws-cdk/issues/38627) で追跡されています。
- 既存の `S3OriginAccessControl` と組み合わせて、S3 Multi-Region Access Point の署名要件を満たす構成が可能になります。

### CloudFront: Origin Access Control に always-amz-auth 署名動作を追加 ([#39196](https://github.com/aws/aws-cdk/pull/39196))

**この機能でできること:**
- 2026-10-12 にリリースされた「CloudFront の Lambda Web Function オリジン」サポートに対応するため、OAC で `always-amz-auth` 署名動作が利用可能になりました。
- この動作では、オリジンリクエストが常に署名され、ビューワーの `Authorization` ヘッダーがそのまま Lambda 関数に渡されます。

**使用例:**

```typescript
import * as cloudfront from 'aws-cdk-lib/aws-cloudfront';

// Lambda Web Function (リージョナルエンドポイント) 向けの OAC
const oac = new cloudfront.FunctionUrlOriginAccessControl(this, 'LambdaOac', {
  // sigv4 + always-amz-auth の組み合わせ (リージョナル Web Function 用)
  signing: cloudfront.Signing.SIGV4_ALWAYS_AMZ_AUTH,
});

// 動作を単独で指定する場合
const customSigning = new cloudfront.Signing({
  protocol: cloudfront.SigningProtocol.SIGV4,
  behavior: cloudfront.SigningBehavior.ALWAYS_AMZ_AUTH,
});
```

**ポイント:**
- `Signing.SIGV4_ALWAYS_AMZ_AUTH` はリージョナルエンドポイント向けで、既存の `FunctionUrlOriginAccessControl` (lambda 型 OAC を作成) と組み合わせて使用します。
- グローバル Web Function エンドポイント向けの `Signing.SIGV4A_ALWAYS_AMZ_AUTH` は、[#38629](https://github.com/aws/aws-cdk/pull/38629) の `SIGV4A` 対応が入ったことで利用可能になります。
- `WebFunctionOrigin` L2 コンストラクト自体は別の Issue で追跡されています。

### CodeBuild: 新しいビルドイメージの追加 ([#37588](https://github.com/aws/aws-cdk/pull/37588))

**この機能でできること:**
- 2025-03-25 にリリースされた CodeBuild の新しいマネージドイメージに対応する定数が追加されました。

| 定数 | イメージ | ベース OS |
| --- | --- | --- |
| `LinuxBuildImage.STANDARD_8_0` | `aws/codebuild/standard:8.0` | Ubuntu 24.04 |
| `LinuxBuildImage.AMAZON_LINUX_2023_6` | `aws/codebuild/amazonlinux-x86_64-standard:6.0` | Amazon Linux 2023 |
| `LinuxArmBuildImage.AMAZON_LINUX_2023_STANDARD_4_0` | `aws/codebuild/amazonlinux-aarch64-standard:4.0` | Amazon Linux 2023 (ARM) |

**使用例:**

```typescript
import * as codebuild from 'aws-cdk-lib/aws-codebuild';

// Ubuntu 24.04 ベースの最新 Standard イメージ
new codebuild.Project(this, 'UbuntuProject', {
  environment: {
    buildImage: codebuild.LinuxBuildImage.STANDARD_8_0,
  },
});

// Amazon Linux 2023 (x86_64) ベースの最新イメージ
new codebuild.Project(this, 'AL2023Project', {
  environment: {
    buildImage: codebuild.LinuxBuildImage.AMAZON_LINUX_2023_6,
  },
});

// Amazon Linux 2023 (ARM) ベースの最新イメージ
new codebuild.Project(this, 'ArmProject', {
  environment: {
    buildImage: codebuild.LinuxArmBuildImage.AMAZON_LINUX_2023_STANDARD_4_0,
  },
});
```

## バグ修正

### API Gateway: ロググループ出力先 ARN による Stage の恒久的なドリフト ([#38816](https://github.com/aws/aws-cdk/pull/38816))

- `LogGroupLogDestination` が CloudWatch Logs の `Arn` 属性 (末尾に `:*` が付く形式) をそのまま使用していたため、API Gateway の実体 ARN (`:*` なし) と一致せず、CloudFormation が Stage のドリフトを永続的に報告していました。
- バグ修正用フィーチャーフラグ `@aws-cdk/aws-apigateway:logGroupDestinationArnWithoutWildcard` を `true` にすると、`ArnFormat.COLON_RESOURCE_NAME` を用いて `:*` を除いた ARN を再構築し、インポートされたロググループの account / region も保持します。
- 既存のアプリケーションの挙動を壊さないために、未設定の環境ではこれまでの `Fn::GetAtt [LogGroup, Arn]` の挙動が維持されます。新規プロジェクトでは `true` が推奨値です。

```typescript
// cdk.json などの context に推奨フラグを設定
{
  "context": {
    "@aws-cdk/aws-apigateway:logGroupDestinationArnWithoutWildcard": true
  }
}
```

### Bedrock AgentCore: Runtime の annotations を acknowledge できない ([#38770](https://github.com/aws/aws-cdk/pull/38770))

- `aws-bedrockagentcore` の `Runtime` コンストラクトが `Annotations.addInfo()` / `addWarning()` を使っており、固有 ID が割り当てられていなかったため、警告や情報メッセージを acknowledge できませんでした。
- 以下の ID を持つ `addInfoV2()` / `addWarningV2()` に置き換えられ、`Annotations.acknowledge*` で抑制できるようになりました。
  - `aws-cdk-lib.aws-bedrockagentcore:containerUriValidationSkipped`
  - `aws-cdk-lib.aws-bedrockagentcore:iamRoleCrossAccount`
  - `aws-cdk-lib.aws-bedrockagentcore:iamRoleCrossRegion`

### core: Nested Stack で construct と template の紐付けができない ([#39141](https://github.com/aws/aws-cdk/pull/39141))

- Cloud Assembly が親スタックのテンプレートしか把握できず、`NestedStack` や `ProductStack` が独自に生成するテンプレート内のリソースの論理 ID を解決できない問題がありました。
- Stack を生成する construct にメタデータを追加することで、正しいテンプレートからリソースを検索できるようになり、各種ツールでのリソース追跡が改善されています。

### core: 未解決の Tags プロパティトークンを保持 ([#37759](https://github.com/aws/aws-cdk/pull/37759))

- `CfnInclude` が、`Tags` プロパティ全体を `Fn::If` でラップする CloudFormation テンプレートの読み込みに失敗していました（`Invalid tag input expected array of {key, value}` エラー）。
- `TagManager` を更新し、プロパティレベルの未解決トークンを保持したまま synth できるようになりました。リテラル値の tag 解析はこれまで通り動作します。

---

### core: 異なるメッセージの検証結果が紛らわしく結合される ([#39132](https://github.com/aws/aws-cdk/pull/39132))

- `CloudFormationValidatePlugin` が診断結果を `ruleId` と severity のみでグルーピングしていたため、最初の診断のメッセージ (プロパティパスを含む) が同じルールの別リソースに適用されて表示されていました。
- グループ化のキーに description を追加することで、異なるメッセージの診断は別々の violation として報告され、各リソースが自身のメッセージと値で表示されるようになりました。同一メッセージの場合は従来通り 1 つの violation にまとめられます。

### stepfunctions: デフォルトの StateMachine IAM ロールに confused deputy 対策が欠けていた ([#37688](https://github.com/aws/aws-cdk/pull/37688))

- `StateMachine` に IAM ロールを明示的に渡さない場合に作成されるデフォルトロールの TrustPolicy が `states.amazonaws.com` に対して無条件に許可を与えており、[cross-service confused deputy 対策のベストプラクティス](https://docs.aws.amazon.com/step-functions/latest/dg/procedure-create-iam-role.html#prevent-cross-service-confused-deputy)に従っていませんでした。
- 修正後は、以下の `Condition` が自動で付与されます。

```typescript
// 自動生成される TrustPolicy の Condition セクション
{
  conditions: {
    ArnLike: {
      'aws:SourceArn': `arn:aws:states:${stack.region}:${stack.account}:stateMachine:*`,
    },
    StringEquals: {
      'aws:SourceAccount': stack.account,
    },
  },
}
```

- カスタム IAM ロールを渡している場合は影響を受けません。デフォルトロールを利用している場合、`cdk diff` で TrustPolicy の変更が表示されます。

## Alpha モジュール

### bedrock-alpha: VectorKnowledgeBase L2 コンストラクトを追加 ([#38883](https://github.com/aws/aws-cdk/pull/38883))

**この機能でできること:**
- `@aws-cdk/aws-bedrock-alpha` に Amazon Bedrock のベクトル Knowledge Base 向け L2 コンストラクトが追加されました。これまで Agents / Guardrails / Prompts / Inference Profiles 用の L2 のみでしたが、Knowledge Base にも対応しています。
- Bring-your-own-vector-store 設計で、既存の OpenSearch Serverless コレクションとベクトルインデックスを `VectorStore.openSearchServerless()` 経由で渡します (L2 は OpenSearch コレクション / データアクセスポリシー / インデックス自体は作成しません)。
- マルチモーダル取り込み用の補助 S3 バケットもオプションで設定可能で、`KnowledgeBaseOpenSearchServerlessStorage` / `KnowledgeBaseSupplementalDataStorage` の mixin を直接 `CfnKnowledgeBase` に適用することもできます。

**使用例:**

```typescript
import * as bedrock from '@aws-cdk/aws-bedrock-alpha';
import * as iam from 'aws-cdk-lib/aws-iam';

const kb = new bedrock.VectorKnowledgeBase(this, 'KnowledgeBase', {
  // 既存の OpenSearch Serverless コレクション / インデックスを指定
  vectorStore: bedrock.VectorStore.openSearchServerless({
    collectionArn: 'arn:aws:aoss:us-east-1:123456789012:collection/abc123',
    vectorIndexName: 'my-vector-index',
    vectorField: 'vector',
    textField: 'text',
    metadataField: 'metadata',
  }),
  // 埋め込みモデル (BedrockFoundationModel.grantInvoke() が自動で付与される)
  embeddingModel: bedrock.BedrockFoundationModel.TITAN_EMBED_TEXT_V2_1024,
});

// 利用者側に Retrieve / RetrieveAndGenerate 権限を付与
const consumer = new iam.Role(this, 'Consumer', {
  assumedBy: new iam.ServicePrincipal('lambda.amazonaws.com'),
});
kb.grantRetrieve(consumer);
kb.grantRetrieveAndGenerate(consumer);

// 既存 Knowledge Base をインポート
const imported = bedrock.VectorKnowledgeBase.fromKnowledgeBaseAttributes(this, 'Imported', {
  knowledgeBaseId: 'ABCDEFGHIJ',
  executionRoleArn: 'arn:aws:iam::123456789012:role/kb-service-role',
});
```

**ポイント:**
- OpenSearch Serverless ベクトルストアでは、Knowledge Base サービスロールにコレクション ARN への `aoss:APIAccessAll` が自動付与されます。
- 補助 S3 ストレージを指定した場合は、`s3:ListBucket` (バケット) と `s3:GetObject` / `s3:PutObject` / `s3:DeleteObject` (バケット内オブジェクト) が付与されます。
- `grantRetrieveAndGenerate` では `bedrock:RetrieveAndGenerate` がリソースレベルの権限をサポートしないため、`Resource: *` が付与される点に注意してください。

### ec2-alpha: RFC 1918 外の有効なセカンダリ CIDR ブロックを許可 ([#36873](https://github.com/aws/aws-cdk/pull/36873))

- `VpcV2` の `validateIpv4address` が、AWS 側では許可されるセカンダリ CIDR ブロックの組み合わせを synth 時に拒否していました。例えば `10.x` のプライマリに対して `198.18.0.0/26` や `100.64.0.0/16` のセカンダリを追加しようとすると `CIDR block should be in the same RFC 1918 range in the VPC` で失敗していました。
- [IPv4 CIDR block association restrictions](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-cidr-blocks.html#add-cidr-block-restrictions) の表に沿って検証ロジックを修正しました。
  - RFC 1918 プライマリは、同じ RFC 1918 範囲、パブリックルーティング可能なブロック、`100.64.0.0/10` を受け入れます (他の RFC 1918 範囲は拒否)。
  - 非 RFC 1918 プライマリ (パブリックルーティング可能 or `100.64.0.0/10`) は RFC 1918 ブロックを拒否します。
  - `198.19.0.0/16` は常に拒否されます。
- これまで受け入れられていた組み合わせは引き続き受け入れられ、`172.17.0.0`〜`172.31.255.255` が `172.16.0.0/12` の一部として認識されるようになっています。

### redshift-alpha: ユーザーパスワードやコメント内のバックスラッシュが保持されない ([#39306](https://github.com/aws/aws-cdk/pull/39306))

- Redshift はプレーン文字列リテラル内のバックスラッシュをエスケープとして解釈するため、ユーザーパスワードやテーブル / カラムコメントにバックスラッシュが含まれると、値が改変されたり文を失敗させる問題がありました。
- `quoteLiteral` でシングルクォートを倍にする前にバックスラッシュをエスケープするようにし、`CREATE USER` / `ALTER USER` のパスワードと `COMMENT ON TABLE` / `COMMENT ON COLUMN` のテキストに適用しています。
- `User` の `excludeCharacters` に Redshift ドキュメントで禁止されている `'`、`"`、`/`、`@` が含まれていない場合に、acknowledge 可能な synth 警告が追加されました (バックスラッシュは Redshift が escape 済みの `\` を受け付けたため警告対象から除外)。
- アップグレードによって既存のパスワードやコメントの値は変更されません。次回同じコメントを送信した際に、`\n` などのエスケープがリテラルとして保存されるようになります。

## 破壊的変更

L1 リソースは CloudFormation Resource Schema から自動生成されており、CloudFormation の実体を正確に反映するために以下の型変更が行われています。

### aws-cloudwatch: AnomalyDetector ([#39139](https://github.com/aws/aws-cdk/pull/39139))

- `AWS::CloudWatch::AnomalyDetector` の `Id` 属性が削除されました。

### aws-glue: Table ([#39139](https://github.com/aws/aws-cdk/pull/39139))

- `AWS::Glue::Table` の `Id` 属性が削除されました。
- `IcebergInput.MetadataOperation` が `json` から `string` に型が狭まりました。
- `IcebergTableInput.Properties` が `json` から `Map<string, string>` に型が狭まりました。

**変更前:**

```typescript
new glue.CfnTable(this, 'Table', {
  // ...
  tableInput: {
    // Properties が任意の json を受け付けていた
    icebergInput: {
      metadataOperation: { someKey: 'value' } as any,
    },
  },
});
```

**変更後:**

```typescript
new glue.CfnTable(this, 'Table', {
  // ...
  tableInput: {
    icebergInput: {
      // string のみ受け付ける
      metadataOperation: 'CREATE',
    },
  },
});
```

### aws-iot: PolicyPrincipalAttachment ([#39139](https://github.com/aws/aws-cdk/pull/39139))

- `AWS::IoT::PolicyPrincipalAttachment` の `Id` 属性が削除されました。

### aws-quicksight: Analysis / Dashboard / Template ([#39139](https://github.com/aws/aws-cdk/pull/39139))

- `AWS::QuickSight::Analysis` / `AWS::QuickSight::Dashboard` / `AWS::QuickSight::Template` の `SheetLayoutGroupMember.Type` が `json` から `ELEMENT` / `GROUP` の string enum に型が狭まりました。

**移行方法:**
- 上記の属性 / プロパティを TypeScript / Python などの typed なコードで参照している場合、コンパイルエラーとなるため利用箇所を見直してください。
- 削除された `Id` 属性については、代替となる `Ref` やリソース名ベースの参照に置き換えてください。
- 型が狭まったプロパティは、CloudFormation が実際に受け付ける値 (string や `Map<string, string>`) に合わせて値を渡してください。

## まとめ

v2.274.0 では、CloudFront OAC の `sigv4a` / `always-amz-auth` 対応や CodeBuild の新ビルドイメージなど、最新の AWS サービス機能に追従する更新に加え、Nested Stack や Step Functions デフォルトロール、API Gateway Stage ドリフトなど、実運用で発生していた問題の修正が多数含まれています。Alpha モジュールでは Bedrock `VectorKnowledgeBase` L2 の登場により、Knowledge Base の構築がより宣言的に行えるようになりました。L1 更新による型変更が複数含まれるため、CloudWatch / Glue / IoT / QuickSight を利用している場合はアップグレード時にビルドエラーが出ないか確認することをおすすめします。
